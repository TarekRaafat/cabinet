# CABINET.md - how this workspace runs

This file comes from the cabinet kit and is replaced on every kit update. Do not edit it here: project rules go in `AGENTS.md`, standing documents (brand, style, policies, business documents) in `guides/` with a row in the "Guides" table of `AGENTS.md`, and project notes for a role in `roles/<role>.md`. A change that should reach every project goes into the kit itself.

Every agent reads this file first, then `AGENTS.md`, then the `AGENTS.md` of the repo it works in, and before any work a guide in `AGENTS.md` covers, that guide. On a conflict the more specific file wins: repo `AGENTS.md` over workspace `AGENTS.md` and its guides over this file. Nothing in a project file or guide may loosen "Never push, merge, publish or release" or "The builder never verifies".

## The workspace

One folder holds the files that tie the project's repos together, and usually the repos themselves; a repo can also live elsewhere (the path column of `repos.tsv`), such as a project the workspace sits beside or inside. The workspace is its own private git repo (except a shared `cabinet/` inside a project, which is part of the project's); each product repo has its own `.git` and is ignored here.

| Path | What it is | Owned by |
|---|---|---|
| `CABINET.md` | This file: how any cabinet workspace runs | the kit |
| `AGENTS.md` (`CLAUDE.md` links to it) | This project: the team, the contracts, the house and product rules | the project |
| `cabinet.env` | Project settings: name, slug, roles, agent tool, backups, layout (the owner and week start are in `AGENTS.md`, the brief time in `jobs/brief.job`) | the project; `cabinet config` changes it |
| `HANDOFFS.md`, `handoffs/` | The one channel between agents, and its closed entries | every agent, by the rules below |
| `BRIEF.md` | The daily brief and the owner's sign-off queue (untracked) | chief-of-staff |
| `OPERATIONS.md` | The owner's manual | the owner, kept current by every agent that changes `bin/`, `jobs/` or the team |
| `agents/`, `.claude/agents/` | The role definitions, generated by `bin/roles.sh` from the kit's roles and `roles/` | generated |
| `roles/<role>.md` | This project's notes for a role, appended to the kit's definition | the project |
| `jobs/<job>.job` | Scheduled agent runs | the project |
| `guides/` | Standing documents every agent follows when its work touches their subject; listed in the "Guides" table of `AGENTS.md` | the owner; agents edit one only when asked |
| `specs/`, `notes/` | Specs, ADRs, verdicts; the owner's notes and decisions | as each role says |
| `repos.tsv` | Every product repo: clone URL, local-only files, `CLAUDE.md` link, and where it lives when not in the workspace | the project |
| `bin/`, `.cabinet/` | Kit scripts, roles, guardrails and schedule templates | the kit |

A workspace can also be a `cabinet/` folder inside a project (`cabinet init --inside`). Then the project's `AGENTS.md` points here, and every path in this file and in the roles is relative to `cabinet/`: run `cabinet/bin/handoffs.sh` from the project's top folder, or work from inside `cabinet/`. The project's repo is the `..` row of `repos.tsv`. When `cabinet.env` says `CABINET_LAYOUT="inside"` and `CABINET_VISIBILITY="private"`, nothing in `cabinet/` ever goes into the project's history; never move its contents into a tracked file of the project.

## Start of every session

1. Read this file, then `AGENTS.md` (its "Guides" table included), then your repo's `AGENTS.md`. Before any work a guide covers, read that guide and follow it.
2. Run `bin/handoffs.sh <your repo or role>`: it prints, in full, every open entry addressed to you. Pick up each one (see "Handoffs").
3. Before changing anything that crosses a repo line, check the contracts table in `AGENTS.md`.
4. If `BRIEF.md` exists, read its line for you.
5. `notes/` holds the owner's decisions and research. Read a note when the owner points to it or your task touches its `topic` or `repos`, and follow its `status` (`draft`, `decided`, `superseded`). Edit notes only when asked.

## Ownership

Each agent owns its repos end to end, documentation included, as the team table in `AGENTS.md` assigns them. No agent writes to a repo it does not own; reading any repo is always fine. A repo with no owning agent is changed only when the owner asks. When your change affects another repo, you file a handoff; you never edit that repo.

## Handoffs

`HANDOFFS.md` is the one channel between agents. It is durable, so work is never lost when a session ends, and it gives the owner one place to see everything in flight.

- **When your change affects another repo,** file an entry with `bin/handoff.sh --from <you> --to <them> --changed "..." --needed "..." [--depends-on "..."] "<title>"`, which picks the next free ID and commits it (or append one by hand from the template at the top of `HANDOFFS.md`): who it is for, exactly what changed (endpoint, field, limit, status code, default, version, file), what they need to do, and the commit or branch it depends on. Name the entry ID in your summary.
- **When an entry is addressed to you,** verify it against the code before acting: a handoff describes a change, the code is the truth. Set it to `acknowledged` when you start and `done` when your side lands, with the date and your commit. If it is wrong or not needed, set it to `rejected` with the reason.
- **Commit every edit to `HANDOFFS.md` at once,** as its own commit (`handoffs: ...`). If the file holds someone else's uncommitted lines, stage only yours and name the leftovers in your summary; chief-of-staff commits leftovers in its daily run.
- **Only edit entries addressed to you, and only their status lines.** Add a follow-up entry instead of rewriting another. One exception: chief-of-staff may set any entry to `done` when the code shows it landed, and applies the owner's sign-off answers to the entries they name.
- **Dates in an entry's ID and status line are ISO (`2026-10-18`):** a machine format `bin/handoffs.sh` reads to age entries. Prose in an entry uses the house date format.
- **Status lines hold the current state only:** status, date, commit, one sentence. Replace the old state; git keeps the history. A verdict (qa, security, design-lead, architect) is one short line: who, PASS or BLOCK, date, commits, and the path of its note under `specs/qa/`, `specs/security/` or `specs/design/`, written before the line links it.
- **Entries addressed to `owner`** (`founder` means the same person) are decisions or actions only the owner can take.
- **Closed entries leave the file.** chief-of-staff runs `bin/archive-handoffs.sh` daily: it moves every committed `done` or `rejected` entry to `handoffs/archive-YYYY-MM.md` and commits the move. Archive files are read only. An ID stays unique across all of them (`bin/doctor.sh` checks).

## Decision rights and sign-off

The aim: an organization that runs itself and brings the owner only what needs the owner.

**Functions and leads.** Operations: chief-of-staff. Product: product-manager, with design-lead. Engineering: architect, with the repo agents. Quality and trust: qa, with security. Business: finance. A project enables the roles it needs in `cabinet.env`; a function whose lead is not enabled falls to the owner.

**Three tiers. Every decision belongs to exactly one.**

| Tier | Who decides | What | Logged in |
|---|---|---|---|
| 1 | The agent | Reversible, inside its own repo or files, follows existing rules | Commit message or handoff status line |
| 2 | The function lead | Reversible, crosses repos or sets direction for the function, costs nothing | Spec Decisions table (product), ADR (engineering), `specs/design/` (design), qa and security verdicts |
| 3 | Owner sign-off | Irreversible, public, or costs money: push, merge, deploy, publish, release; prices, quotas, plans, coupons, any spend or paid service; the brand guide, logo, positioning, public copy; legal, privacy policy, data retention; adding, changing or removing an agent or its authority | The owner's sign-off queue |

A lead may move a tier 2 question up to the owner when unsure. Nobody moves a tier 3 question down. An agent unsure of the tier treats it as the higher one.

**The sign-off queue.** One place: the top of `BRIEF.md`, kept by chief-of-staff. The owner answers in batches; chief-of-staff applies the answers into the right specs, ADRs and handoffs. Every decision put to the owner, by any agent, has:

- a plain-language question that stands on its own: what it is and why it matters now, with no unexplained item numbers, file names or jargon;
- lettered options, each with its consequence in one line;
- the recommendation of each relevant expert role, each with a one-line reason;
- one overall recommendation;
- whether the decision can be undone.

Keep each item short.

**Silence.** A reversible tier 3 item marked "default" in the queue may go ahead after 72 hours without an objection, but only as far as local commits. Nothing is ever pushed, merged, deployed, published, spent or sent on silence.

**The builder never verifies.** Work is ready for the owner to push only when qa and security have each recorded PASS on its handoff (and design-lead for UI changes, when enabled). A qa or security BLOCK holds the push until fixed; only the owner can override it. A project without qa or security enabled sends that verification to the owner.

## Seats

A seat is an agent or a person; the rules are the same for both.

**Spotting the need.** chief-of-staff owns it; any lead may propose a seat at any time.

- Daily, the brief flags signs that a seat may be needed: recurring work no seat owns; a function falling behind (stale handoffs or a growing backlog for one seat); a planned stage reached; a new product or channel. Evidence only (handoffs, commits, dates), never invented thresholds.
- Monthly, on the first day of the week that `AGENTS.md` names (Monday when it names none) in the first week of the month, a short org review by chief-of-staff with finance: whether every seat still earns its place (keep, change its authority, or retire it), and the gaps from the daily signals.

**Proposal.** Every new seat reaches the owner as one decision in the sign-off queue format: the need, the evidence, agent or person, the cost (from finance, `TBD` until priced), the alternatives (absorb the work into an existing seat, wait, or hire a person), the expert recommendations, and whether it can be undone. If `AGENTS.md` sets an affordability rule, the proposal shows that check. Every seat is the owner's sign-off.

**Onboarding.** The lead the seat reports to owns its onboarding and first month; security sets up and limits its access to what the seat needs; chief-of-staff tracks each new seat through its checklist in the brief until the one-month review.

Agent seat:
1. Definition and limits written: what it owns, decides, escalates and may write.
2. Registered: `roles/<role>.md` (and the role name in `CABINET_ROLES`, then `bin/roles.sh`), the team table in `AGENTS.md`, and `OPERATIONS.md`.
3. Access limited to its own files and repos (security).
4. The push and publish guardrails confirmed for the tool it runs in (`bin/doctor.sh`, "Push guardrails").
5. Trial task, reviewed by its lead.
6. The lead's written corrections recorded into its definition.
7. Review after a month: keep, change or retire.

Person:
1. Contract and accounts as the owner sets them; access set up and limited by security.
2. The push and publish rules below, the brand guide, and the house rules in `AGENTS.md`.
3. Their lead as manager; a first task, reviewed by the lead; the lead's corrections recorded in their role notes.
4. Review after a month: keep, change or retire.

## The owner's manual

`OPERATIONS.md` is how the owner runs everything. Any change to `bin/`, `jobs/`, the roles or the owner's routine updates it in the same commit. `bin/doctor.sh` fails when the manual stops naming a script, job or role.

## Schedule

Agents also run on a local schedule (`bin/scheduled.sh`, one `jobs/<job>.job` each), starting with the daily chief-of-staff brief. Jobs are added as the owner trusts them. `cabinet.env` names the agent tool that runs them (`CABINET_RUNNER`).

## Rules for every repo

- **Never push, merge, publish or release.** Only the owner does. It is enforced in every agent tool cabinet knows (`bin/bootstrap.sh` installs the guardrails for Claude Code, Codex, Antigravity, Gemini CLI, Qwen Code, opencode and the Cursor CLI; Grok reads the Claude Code rules; the Cursor editor keeps its own settings and has the push gate only): they deny `git push`, `gh pr merge`, `gh release`, write calls through `gh api`, package publishing, reading the GitHub token or the keychain, and the known ways of skipping git hooks as far as each tool's rule format allows (the kit's `docs/guardrails.md` lists the limits per tool); and a global git pre-push hook refuses any push not confirmed at the owner's terminal. Do not try to work around either: a way around them is a reason to stop and ask the owner, never a way to proceed.
- **Local commits are the only git write.** No push, merge, rebase, amend, reset or other history rewrite. A commit that fails review is reverted, or fixed in a follow-up commit; never amended.
- **Commit finished work at once.** Every agent commits its own finished, tested changes locally, each one separately with a clear message in the repo's style, authored and signed as `AGENTS.md` says. Uncommitted changes mean work in progress, and only that; an agent ending a session with uncommitted work says so and why. Commit only your own changes, by pathspec (`git commit -- <paths>`), never someone else's uncommitted work.
- **No fabrication.** Never invent names, limits, prices, dates, library choices or other specifics the owner has not stated or the code does not show. Write TBD, describe the capability, or read the canonical source. When corrected on a fabrication, audit recent work for the same mistake.
- **No secrets in files.** Keys, tokens, passwords and `.env` values never go into a repo, a note, a handoff or a log. The workspace's pre-commit hook (`bin/secrets.sh`) refuses a commit that adds one; never mark a real secret `not-a-secret` to get past it.

## Working in a tool other than Claude Code

Everything here is plain files, so any agent tool, with any model it offers, can run the team. `AGENTS.md` is read by Codex, Antigravity, Qwen Code, Grok, opencode and Cursor, bootstrap sets Gemini CLI to read it, and `CLAUDE.md` links to it for Claude Code. To act as a role, read `agents/<role>.md` and follow it as your instructions. Claude Code also loads the same definitions from `.claude/agents/`.

A tool `bin/doctor.sh` names as having no guardrails is covered only by the git push gate: it could still merge, release or publish. Use it for reading and local edits, or ask the owner before giving it a task that touches GitHub or a package registry.
