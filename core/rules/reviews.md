# Evidence and verdicts

Read with `CABINET.md`, which every rule here builds on. For every agent that hands work on with something to show, and every reviewer (qa, security, design-lead, code-reviewer, dba, architect, and any role that records PASS or BLOCK).

- **Evidence is a link the owner can click.** Add `--evidence <file or URL>`, once for each, for what shows the work: a screenshot of each screen and state, a short recording, a link to try it, or a saved command output for work with no screen. A file is copied to `specs/evidence/<ID>/` and committed with the entry; its `Evidence:` line links it from the workspace root, so it opens from `HANDOFFS.md` and `BRIEF.md`. Evidence that comes later (after a fix, or asked for by a BLOCK) is added by the sender to its own entry with `bin/handoff.sh attach <ID> <file or URL>... --from <you>`, so the entry always holds everything that shows the work.
- **A verdict is one line in one format,** written only with `bin/handoff.sh record <ID> --role <you> <PASS|BLOCK|CHANGES> --commits <hash,...>|none --note <file>`, never by hand: below the entry's other lines, one line per reviewer, replaced on each re-check: `- Verdict: <role> <PASS|BLOCK|CHANGES> <YYYY-MM-DD> <commits> <note>` (`none` for commits when the work changes no repo), for example `- Verdict: qa PASS 2026-10-20 a1b2c3d,e4f5a6b specs/qa/2026-10-20-login.md`. Commits are short hashes joined by commas, with no spaces; the note is the reviewer's file under `specs/` (letters, digits, `.`, `_`, `-` and `/` only), written and committed before you record, and holds the details: what was run, each failure or finding, the fix. `record` refuses a note that is not committed, a verdict by the entry's own sender, a qa PASS on an entry with no evidence, and a PASS on commits that change a path under "Hard to undo" in `AGENTS.md` while the entry has no `- Way back:` line (its sender adds one with `bin/handoff.sh attach <ID> --way-back "..." --from <sender>`); `bin/doctor.sh` checks lines written by hand (`handoffs.verdicts`, `handoffs.evidence`). Verifying work with no handoff? File one first, so the verdict has an entry.
- **qa never records PASS without evidence** that matches what it saw: missing, partial or not matching, it records BLOCK naming what is missing, and the sender adds it with `bin/handoff.sh attach`. `record` refuses a qa PASS on an entry with no evidence.
- **Name every commit of the work,** not only the latest fix: a verdict covers the commits it names. Every commit any verdict on the entry names is the work, and a PASS that does not cover all of them no longer counts (it is "stale"), so after a fix each reviewer records again.
- **A re-review reads only what changed.** A reviewer that already recorded a verdict on an entry and is asked again (its PASS stale, or its BLOCK or CHANGES fixed) reads its own last note, the commits after those its last verdict names, and the files those commits change, and runs only the test sections those files touch (`bin/handoff.sh run` names both sets of commits); security's `record` still runs a critical area's check, and the verdict still names every commit of the work. The builder still runs the full suite once per review round and attaches the logs. The reviewer checks the fix against each of its own earlier findings and says in its note, for each one, whether it is fixed. Any reviewer may read more than the fix, up to the whole change, when the fix touches a file, function or behavior its last note covered, and says so in its note.
- **A verdict is not a status.** Record it and leave the entry's status line alone: the entry stays open until its work is pushed, and chief-of-staff then closes it. A PASS, BLOCK or CHANGES written anywhere else, such as a status line, is not read (`bin/doctor.sh`, `handoffs.unread-verdicts`).
- **Readiness is computed.** `bin/handoff.sh list --json` gives each entry the reviewers it needs (each one it is addressed to; for code, qa, security and code-reviewer, and design-lead when a web or mobile builder sent it, each when on the team), and which are missing, blocking or stale. `bin/handoff.sh list --ready` lists the work ready for the owner to push. A builder addresses every reviewer whose subject the change touches (dba for a schema, a migration or a heavy query), since that is how the script knows. Where a sub-team role covers the sender's work for a lead, its verdict counts for the lead's, and during its trial the lead's PASS is needed too (`.cabinet/rules/seats.md`, "Sub-teams").

## Critical areas

A project declares the parts where a mistake costs more under "Critical areas" in `AGENTS.md`: each area's paths, the reviewers it needs as well as the usual ones, the evidence they must see, and optionally a check, a command in `tools/`. The kit knows nothing about what an area is; it only applies what the row says.

- **Which work.** Work touches an area when its commits change a file under the area's paths, or when its spec (or the spec of the work it reviews) names the area in `areas`, so the reviewers are known from routing, not only at the end. `bin/handoff.sh list --json` gives each entry its `areas`.
- **Its reviewers.** Each is added to what the work needs, so it is not ready to push until they pass (`bin/handoff.sh run` runs them). A reviewer the row names that is not on the team holds the work until the row or the team is fixed (`bin/doctor.sh`, `areas.declared`).
- **Its evidence.** The row says what the reviewer must see, in plain words; the reviewer judges it, and records BLOCK naming what is missing.
- **Its check.** When one of the area's reviewers records PASS, `bin/handoff.sh record` first runs the area's check at the work's commits, in the workspace, with `CABINET_AREA`, `CABINET_HANDOFF` and `CABINET_COMMITS` set and the run's time limit. It refuses the PASS when the check fails, and keeps its output as evidence on the entry (`specs/evidence/<ID>/check-<area>.txt`). Only a command in `tools/` runs, never through a shell.
