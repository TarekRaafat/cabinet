# Changelog

Each version says what changed and anything a workspace must do by hand after `npx cabinet update`, which prints these entries.

## 0.2.1 - Unreleased

- `CABINET.md` and the docs for `handoff add` say that text holding `$`, a backtick or a backslash goes in single quotes or a quoted here-document, never double quotes, since the shell would run it before Cabinet sees it.
- `cabinet handoff list --ready` prints the `cabinet session end <name>` command for work held on a session branch only when the branch name is a session name; a branch made with git whose name holds shell characters is named, with no command to paste.

## 0.2.0 - 29 Oct 2026

Credit roles, color, parallel sessions, and a notice when a newer Cabinet is out. After updating, run `cabinet bootstrap` and add a line for `bin/session.sh` to `OPERATIONS.md`.

### Credit roles

- A commit a role makes in a Cabinet run can credit that role beside you: its message ends with one `Co-authored-by: Cabinet <role> <347351783+cabinet-team[bot]@users.noreply.github.com>` line, which GitHub shows with the Cabinet Team avatar. You stay the author and still push. New options for `cabinet new`, `init` and `config`: `--credit-roles off|on` (`on` for a new workspace, and asked at setup) and `--credit-email <email>|off` (your own GitHub App's bot noreply email). `cabinet config --this-machine --credit-roles off|on` answers for one machine; in a shared `cabinet/`, each machine answers for itself. Only commits made in a Cabinet run are credited (scheduled jobs, `handoff run`, `spec run`, `role draft`), and only new ones: never an amend (a run is refused one), a merge or a squash, nor a commit a rebase or cherry-pick replays. The "Commits." house rule in `AGENTS.md` follows the setting; the concepts page explains it.
- Bootstrap places the credit hook as `prepare-commit-msg` in the global hooks folder, in place of the pass-through stub there (it still runs a repo's own `prepare-commit-msg`, whose failure still stops the commit). A hook of your own there is never replaced. New doctor checks `credit.setting`, `credit.email` and `credit.hook`; new `cabinet next` step `credit-roles`. Every runner now gets the role in `CABINET_AGENT`, not only `custom`.
- In a shared `cabinet/`, off for everyone wins: while the committed setting is off or not set, no machine's runs credit, even one that answered on for itself; a machine's on counts only while the project's setting is on. `cabinet next` asks a machine only then, and `cabinet doctor` (`credit.setting`) says when the project's setting turns this machine's on off.
- After `npx cabinet update`: nothing changes until you answer. `cabinet next` and the brief ask once (`cabinet config --credit-roles on`, or `off`); then run `cabinet bootstrap` to place the credit hook on this machine.

### Color in a terminal

- The `cabinet` command's output is easier to scan in a terminal, in the terminal's own colors: headings, first lines and the command to run next in bold; folders, dates and handoff IDs dim; ok green, notes blue, problems and errors (`cabinet:`) red; and what waits on you in yellow, the terminal's stand-in for the owner's brass: `next`'s step numbers, the digest's sign-off queue and actions, `list`'s WAITING ON YOU, and `owner` in `handoff list`. On a Verdict line of `handoff list <name>`, PASS is green and BLOCK and CHANGES red. `cabinet doctor` keeps its colors and shows its section headings in bold.
- `cabinet update` and `cabinet changelog` show the changelog for reading in a terminal: versions and headings in bold, no `##`, backticks or asterisks, list items and paragraphs wrapped at words to the terminal's width (`COLUMNS` when set, else 80 when the width is unknown), and a word longer than the line kept whole.
- In a terminal, control characters from project text show as `?`: handoff titles and entries in `handoff list`, the brief's sign-off queue and actions in `digest`, and project names and folders in `digest`, `list` and `next`, so an escape sequence written into a handoff or a brief can no longer hide or rewrite what you see. UTF-8 text is unchanged, and piped, in a file or with `--json` the text is as written.
- The same holds for the rest of the commands that print project text: `cabinet doctor` (its messages quote settings such as `CABINET_CREDIT_ROLES`, and names), `role list` (titles and names from `roles/`), `repo list` (folders and owners; a skipped `repos.tsv` row's name shows its control characters as `?` everywhere), `spec check` (statuses and problems) and `status` (folders). Piped and with `--json`, the text is as written.
- Output is styled only when it goes to a terminal, `NO_COLOR` is unset or empty and `TERM` is not `dumb`. Piped, written to a file (`digest --write`), with `--json`, or with `NO_COLOR=1`, every command prints the same text as in 0.1.3, byte for byte, so agents and scripts read what they always did. `cabinet doctor` now also leaves color out with `TERM=dumb`.

### Parallel sessions

- `cabinet session start [name] [--repo <repo>]` gives an agent session a folder of its own: a git worktree of a repo at `sessions/<repo>/<name>/` (`cabinet/sessions/...` inside a project), on a new branch `session/<name>` from the repo's current branch, ignored by the workspace's git. Its commits, uncommitted changes and test runs are its own, so several sessions (yours, a teammate's, the team's roles) work in one repo at once without seeing or sweeping each other's changes. It prints the folder, says when the main folder has uncommitted changes the session does not get, and prints a `## Session setup` section from the repo's `AGENTS.md`. Names are 1 to 40 lower-case letters, digits and hyphens; with none, the date and a number. Sessions need git 2.17 or later.
- `cabinet session list [--json]`: each session's repo, branch, folder, commits ahead, uncommitted files, whether it is merged and when it started; a folder deleted by hand shows as gone, with the prune command, and the doctor notes it (`sessions.gone`). `cabinet session end <name>`: its commits, the handoffs that name them, and the command that brings them into the repo's current branch, which you run (no Cabinet command merges, rebases or pushes); then it removes the folder when nothing in it is uncommitted, and keeps the branch.
- `cabinet handoff list --ready` holds back passed work whose commits are only on a session branch, and names the branch; `handoff list --json` gains `session_branch`. The brief lists every session not merged under "Actions for the owner". Backups save each session's uncommitted changes and untracked files, `backup verify` checks each one (`<repo> session <name>`), and restore brings a session back as its worktree, or into `recovered/` where the repo already exists.
- Git actions that can be undone (an amend, a rebase, a reset without `--hard`, a local merge, a cherry-pick, a revert, a branch, a stash) now run when you ask for them in a session, with the way to undo them said after; never on an agent's own initiative, nor from a handoff, a job or anything it read. Before a command that sweeps or drops uncommitted changes, an agent checks every change is its own and saves a snapshot (`git stash create` and `git stash store`). Push, a merge on GitHub, releases, publishing and any force stay with you as before, and no guardrail deny rule changed. The rule's name is now "Never push, merge on a shared host, publish or release", in `CABINET.md`, the builders' and seats' rules and the chief-of-staff role.
- An agent may amend its own newest commit without asking, while it is not pushed and no handoff, verdict or note names it; once one does, a fix is a new commit. Unattended runs still refuse any amend.
- Unattended runs never rewrite: in a Cabinet run, the credit hook now refuses `git commit --amend` in every form (and `-c` or `-C`), and a new kit hook, `pre-rebase`, refuses `git rebase`. Both run a repo's own hook of the same name first. Your terminal and interactive sessions are not affected. On macOS a new commit whose `-m` message mentions `--amend` is refused too; give that message with `-F <file>`. A rebase that skips its hook is refused only by the tools whose deny rules match `--no-v`; the guardrails page names the tools that are not covered. New doctor check `guardrails.run-refusal`.
- After `npx cabinet update`: run `cabinet bootstrap` to place the new hooks on this machine, and add a line for `bin/session.sh` to `OPERATIONS.md` (the doctor's `manual.complete` names it until you do). A `pre-rebase` of your own in the global hooks folder is left as it is, and the doctor says the run refusal is not installed.

### Commands

- The release notice: `cabinet next` (a step, `update`), `cabinet status` (`latest:` and `Run:`, and `latest` in `--json`) and the doctor (a note, `kit.newer`) say when a newer Cabinet is out, with the command that takes it, and the brief puts it under "Actions for the owner". It only tells; nothing updates. At most one request a day per machine, in the background (no command waits for it): `npm view @tarekraafat/cabinet version --no-update-notifier`, through your own npm and its settings, from Cabinet's log folder. Like any npm request, it carries npm's usual details and your npm login when you are logged in, and nothing about the project. Off with `cabinet config --update-check off` (`--this-machine` for one machine), or `CABINET_UPDATE_CHECK=off`, `NO_UPDATE_NOTIFIER` or `CI` in the environment. `cabinet outdated` now compares by version order, so `update_available` in `--json` is false for a kit newer than the registry; its `--json` gains `command`; and its advice for a pinned kit is now `npm install @tarekraafat/cabinet@latest && cabinet update`, since `npm update` keeps to the pin's range and never reaches 0.2.0 from `^0.1.x`.
- Choose the model: `cabinet new`, `init` and `config` take `--model <name>|off` (`CABINET_MODEL`, asked at setup right after the agent tool; Enter keeps the tool's default), and a job file can set `MODEL="<name>"` for its own runs. Every run passes it with the tool's own `--model` option (`custom` gets `$CABINET_MODEL`); with none set, every tool gets exactly the command line it got before. A name is letters, digits and `. _ : / @ -`, up to 100, not starting with `-`: anything else is refused before it is written, and before any run starts. The doctor's new checks `model.name` and `model.exists` say whether the tool lists the model, for codex, antigravity, grok, opencode and cursor, which can list their models without a run; Claude Code, Qwen Code and custom get a note. No check ever makes a paid run. The setup guide has a table of each tool's option and list.
- `cabinet push-check`: what is ready to push, per repo, before you push. For the workspace and each repo, the branch, its upstream, each unpushed commit with the handoffs whose verdicts name it (or `no handoff`), the size of the change, and each handoff's reviews: ready, or who is missing, blocking or stale. A repo ends `ready to push` only when every unpushed commit is on a ready handoff, else `not ready` with the first reason. Local refs only: it fetches and changes nothing. `--json` for scripts.

### Handoffs

- The loop breaker: `cabinet handoff run` stops for you once the same reviewer has blocked the work more times than `--retries` allows (with the default 2, at the third BLOCK or CHANGES), counted over every run from the history of `HANDOFFS.md`, not only this run's rounds, and names the reviewer and the count. A scheduled run skips it until you run it by hand, `PIPELINE.md` says why, and the brief puts it in your sign-off queue with the options. `handoff list --json` gives each entry `blocks`, the count per reviewer.
- A way back before anything hard to undo: a handoff can say how to undo its change once pushed, released or published, or why there is none, on a `Way back:` line, with `cabinet handoff add --way-back "..."` or later `cabinet handoff attach <ID> --way-back "..." --from <you>` (which replaces it). `cabinet handoff record` refuses a PASS on commits that change a path under "Hard to undo" in `AGENTS.md` while the entry has none, naming the file. Builders add it when they hand such work on, and the brief quotes it beside whether the change can be undone.

### Fixes

- `cabinet handoff run --dry-run` that stops no longer leaves the stopped mark a real stop leaves, so a scheduled run no longer skips work only because a dry run looked at it.
- `cabinet config` checks every setting it writes back to `cabinet.env` before writing anything, the ones it carries over unchanged included, so a value edited by hand that holds `$`, a backtick, a backslash, a double quote or a line break stops it, naming the setting, instead of becoming code the next time a script reads the file. A role's name is lowercase letters, digits and dashes, and a file under `roles/` with any other name is no longer taken as a role.

### Docs

- The concepts page says how to call a role from a session: `@agent-<role>` in Claude Code (`@agent-product-manager`), and in every other tool plain words such as "As product-manager, read agents/product-manager.md and ...", which runs the role inside the current session. The website's tour says the same beside the team.

### Rules

- Every role restates the real problem first: before acting on an owner request, it says in one line the problem the request solves; when a simpler way solves it, or the request would not, it says so with its recommendation and lets you choose before building either; and it names every tool, access, account or file the work needs before it starts, not partway through (`CABINET.md`). product-manager starts a spec's Problem from the real problem and names a simpler option you did not ask for under Decisions.
- The changelog lists changes to what the package ships or what users see; the website gets at most one line per release, for a new page or section. `AGENTS.md` and `CONTRIBUTING.md` say so.

## 0.1.3 - 26 Oct 2026

Commands, a website, and pinned releases. Nothing to do by hand after `npx cabinet update`.

### Commands

- `cabinet config` commits only the files that run wrote, each for the settings that change it, instead of `AGENTS.md`, `OPERATIONS.md`, `package.json` and `jobs/` on every run and the role files whenever setup was due: a brief time or a budget no longer commits `AGENTS.md`, and the role files (`ORG.md`, `agents/`, `.claude/agents/`) go in only when the roles or the name change or `bootstrap` actually ran, and then only those the role build changed, added or removed. ## 0.1.2 - 24 Oct 2026

Fixes and docs. Nothing to do by hand after `npx cabinet update`.

### Commands

- `cabinet update` commits the update itself (`cabinet: update to <version>`, with the pin from `npm update`; an edit of the owner's own elsewhere in `package.json` keeps it and its lockfile out of the commit, and the commit it prints for them names `package-lock.json` only when there is one) in a workspace with its own git, unless the files it rewrites held uncommitted edits of the owner's; then it ends with the commit to run, as before. Its last line is now one short sentence instead of a long command. Where there is nothing to commit (a workspace with no git of its own, or a private `cabinet/` the project ignores) it ends with `Updated to <version>.`, and says "Nothing changed" only when the workspace was already on that version.
- `cabinet config` commits its change (`cabinet config: <the settings changed>`, with the files its settings live in (`cabinet.env`, `AGENTS.md`, `OPERATIONS.md`, `package.json`, `jobs/`, and the role files `ORG.md`, `agents/` and `.claude/agents/` when the roles change or setup is due; `HANDOFFS.md`, `README.md` and `specs/ROADMAP.md` only after a rename, `README.md` after a new slug too, and `repos.tsv` only after a repo is added), so another session's uncommitted edit to one of those files goes into that commit, and every other file, a new handoff of theirs included, stays theirs) in a workspace with its own git that had no uncommitted changes before; otherwise it says to review and commit, as before. `cabinet repo add`, which goes through `config`, commits the same way (`cabinet config: add repo`). With `role add`, `role remove`, `update` and `bootstrap`, these commands now commit their own change; the rest, such as `repo snapshot`, still leave it to review and commit.
- `cabinet version`, in a terminal, shows the approved tagline beside the mark ("One person, a whole team. Build anything with AI agents, and stay in charge."), as does the brand guide's sample of it; it showed an older one.
- `cabinet next` no longer asks to fill the TBDs of a finished `AGENTS.md`: it counted the template's own instructions, which quote `TBD` as code ("write `none` in place of `TBD`"). Only a TBD left to fill counts.
- `cabinet help` shows each group of commands once, with all its commands under it; "Daily" and "Team" appeared twice.
- A mistyped command gets a short answer instead of the whole help: `cabinet: unknown command 'docter'`, `Did you mean: cabinet doctor` when one is near, and `Every command: cabinet help`. It still exits 2.
- A critical area whose name has spaces (`| setup and untrusted values | ...` in `AGENTS.md`) can now be named in a spec's `areas`. `cabinet spec check` split the names into words and refused it as no critical area, and `cabinet handoff list` and the brief did the same with the spec's list, so work routed from that spec missed the area's reviewers. Area names are kept whole, split only on the commas of `areas: [...]`; one-word names work as before.
- `cabinet config --backup-dir <folder>` works in a workspace whose `cabinet.local.env` has no backup folder of its own (any new workspace). It ended with exit 2 and no output, writing nothing; now it lists `backups: off -> <folder>`, writes it and commits it.

### Releases

- The release workflow checks out the full history with its tags, so the check on changes after a release runs on GitHub too; without the tags it passed unseen.
- The tests fail when the test file itself does not parse. Before, a syntax error in it ended the run with success, so a release could have published with no tests run.

### Schedules

- A scheduled run that finishes on its own is no longer reported as stopped by its time limit when the machine slept during it. The limit counts only time awake, but the report compared the clock on the wall, so a morning brief that ran across a sleep and finished was logged as stopped, with exit 124. Now only a run the time limit actually stopped is reported as stopped.

### Docs

- The docs no longer show 0.1.0 as the current version: the README's status line points to the changelog instead of naming a version, and the tutorial and the brand guide show the current one. The tests fail when a doc shows a Cabinet version other than the one in `package.json`, so a release cannot leave the docs behind.
- The README says Cabinet is built and maintained with Cabinet.
- The kit's `AGENTS.md` says several sessions may work in the repo at once, and how each commits only its own changes, leaving the rest as they are (rule 12).
- The README and the recipes no longer end the update steps with `git diff` to review and commit: `cabinet update` commits itself, and prints the commit to run only when it cannot. The commands page says it ends with "Nothing changed" when the workspace was already on that version, and troubleshooting says an unknown command gets one short answer with the closest command, not the list of commands.

## 0.1.1 - 23 Oct 2026

Fixes and release mechanics. Nothing to do by hand after `npx cabinet update`.

### The team

- `cabinet role add` and `role remove` commit their change in a workspace with its own git when the files they touch held no uncommitted edits of the owner's; otherwise they say to review and commit it, as `cabinet config` does (before, they said nothing and left it uncommitted).
- After a release, changes go under the next version: the kit's `AGENTS.md` says a released version is closed and the first change after it opens the next one (patch, minor or major by what changed), and every workspace's builders follow the same rule (`.cabinet/rules/builders.md`), so the owner never tracks it. The tests fail when the kit has changes since a released version that no unreleased section covers.

- Releases publish from GitHub with provenance: publishing a GitHub release runs `.github/workflows/release.yml`, which checks the tag against `package.json`, runs the tests and publishes to npm with `--provenance`, signing in as the package's trusted publisher, with no stored token. The README's release steps say so.
- The release workflow installs zsh before the tests, as the Linux test image does: GitHub's runner has none, and the completion test needs it.

### Docs

- The README says how a Node.js version manager affects a global install: after switching Node versions, install Cabinet again.
- The test of `cabinet update` showing a newer kit's changelog works from whatever version the kit is at, not only from 0.1.0.

## 0.1.0 - 23 Oct 2026

First version.

### Setup and settings

- Installed per workspace as the dev dependency `@tarekraafat/cabinet`; the package names its repository, home page and issue tracker on GitHub, publishes as public, and installs on macOS and Linux.
- Bootstrap commits what a new builder changes (the team table in `AGENTS.md`, `ORG.md`, the built roles), when the workspace has its own git and those files held no uncommitted edits of the owner's; otherwise it says to review and commit them, naming `ORG.md` too.
- Setup commits every file it writes, the org page `ORG.md` included, so a new workspace starts with nothing uncommitted.
- `cabinet new` asks its setup questions in a terminal (name, folder, owner, roles, agent tool, a weekly budget (and a price for a runner that reports only tokens), brief time, week start, writing to the owner, backups, repos); each is also an option, and `--yes` skips them for scripts.
- `cabinet init` adds Cabinet to an existing project: inside it as `cabinet/`, private or shared, or beside it; or makes an existing folder of repos the workspace. Nothing existing is replaced. It fills the project name, description, test commands, repository URL and owner from the project's `package.json` and git, each marked with its source.
- `cabinet config` changes settings after setup: the same questions with the current answers as defaults. It keeps the team tables, roles and schedules in step, and moves schedules on a slug change. `cabinet config --this-machine --backup-dir <folder>|off [--backup-time <time>]` sets backups for one machine only, in `cabinet.local.env`, so each teammate in a shared workspace picks their own folder or none; `--clear` follows `cabinet.env` again.
- `cabinet update` applies the installed kit and shows the changelog since the workspace's version; `cabinet changelog`, `status`, `version` and `outdated`.
- `cabinet version` prints the Cabinet mark in a terminal (seven seats around a table and one open place for the owner), drawn with large dots (`⬤`), or in plain ASCII when the locale is not UTF-8. Piped or redirected, it prints only `cabinet <version>`.
- `cabinet doctor` colors each result's label in a terminal: `ok` green, `note` blue, `FIX` red. No colors when piped or redirected, or when `NO_COLOR` is set. `--json` is unchanged.
- The tagline is "One person, a whole team. Build anything with AI agents, and stay in charge.": in the README, `llms.txt`, the package description, `cabinet help`, the social preview and, shortened to "One person, a whole team. You stay in charge.", `cabinet version`. Cabinet is a productivity kit that amplifies people and never replaces them: agents bring the skills and the hours, and the person brings the vision, the judgment and the final say, so one person works like a whole team or company, alone or in a team. The README says so first, and so do the brand guide, `llms.txt`, the concepts page and `CABINET.md`, which tells every agent it works for the owner and never stands in for them. The README says Cabinet is for one person or a team of any size and for anything agents can build, with what is still made for code first, and opens with "Why Cabinet": where it comes from (its author's own setup for a year and a half across product, design and development, about tenfold his output, and the same for colleagues who tried it) and what it believes.
- The name is written "Cabinet" in sentences and headings across the README, the docs, the roles and the workspace rules; `cabinet` stays lowercase where it is the command, a file or the package.
- Roadmap: one Cabinet per person following a team's shared rulebook, work that is not code made as complete as code, and an inventory of what exists, whose rows and states are proposed for each kind of project (capabilities for an app, tracks for an album, components for a design system).
- Needs git, Node.js 18 or newer and npm (openssl for backups). With an older Node.js, setup, the doctor (`deps.node`) and every script stop with a message that says how to get a newer one, instead of failing on a syntax error. The workspace scripts are bash, and the logic they share is JavaScript in `scripts/lib.js` (a workspace's `bin/lib.js`), run with Node: the owner's manual page, spec checks, handoff readiness and entries, file edits that keep each file's bytes and permissions, the secret scan, time limits, and reading and writing JSON (`json`). The kit's tests and tools need nothing more.
- Set up by an AI agent: `docs/agent-setup.md` is the guide for an agent a person asks to set Cabinet up (the checks, the install, the questions to ask in plain words, the commands for a new or existing project or for work that is not code, `--yes` with `--dry-run` first, `bootstrap` only after showing the person what it changes, checking the result, and what to tell the person). The root `AGENTS.md`, which agent tools load first, sends such an agent there before anything else, and so do the README and `llms.txt`. The README says what setup changes on the machine and how to install from a clone that is kept, and the workspace template says what to write for work without code. The docs check fails when a `cabinet next` step ID or an option the guide uses is missing.
- Roadmap: toward a single download, one file compiled with Bun, once people without Node need it; until then the bash moves to JavaScript one command at a time, when a command is slow or being reworked. New kit logic is JavaScript run with Node, never TypeScript (`AGENTS.md`, rule 3).
- The README opens with the Cabinet mark (`docs/logo.svg`), on its own light tile so it reads the same on light and dark themes.
- `cabinet remove` removes a workspace (its schedules, logs and folder, and inside a project what setup added), refusing work that exists nowhere else unless `--force`.
- Tools first: `cabinet new`, `init` and `bootstrap` check for git, node and npm, name what is missing with the command that installs it here (`brew`, `apt-get`, `dnf` or `pacman`), and in a terminal offer to run it; with `--yes` or `--dry-run` they never install. The doctor reports a missing tool (`deps.required`) and a tool enabled backups need (`deps.backups`: openssl, and `secret-tool` on Linux), `cabinet doctor --fix` installs them after asking (always in a terminal, even with `--yes`), and `cabinet next` shows the step `deps`. Agents are told to pass the command to the owner, never to install system packages themselves.
- Writing to the owner: asked at setup and by `config` after the week start, or `--writing short|standard` on `new`, `init` and `config`, sets a house rule in `AGENTS.md` that every agent follows for the brief, sign-off items and answers (`CABINET.md`, "Writing to the owner"). `short`, for an owner with little time to read or who reads best in small pieces: answer first, one point per line, three points at most, a decision in three lines, no background unless asked; the sign-off queue stays complete and no warning is cut. `config` adds the line to an `AGENTS.md` written before it.
- `--dry-run` for `new`, `init` and `config`. `repos.tsv` takes an optional path column for a repo that lives outside the workspace.

### The team

- Core rules (`CABINET.md`): workspace layout, handoffs, three decision tiers, the sign-off queue, silence, the builder never verifies, seats and onboarding, git and release rules.
- Roles: chief-of-staff, product-manager, architect, qa, security, design-lead, finance. Project notes and project-only roles through `roles/`.
- Optional kit roles, off until turned on with `cabinet config --roles`: `brand-designer` (brand files and graphics), `dba` (migration reviews, database health), `code-reviewer` (PASS or CHANGES on each change's code) and `auditor` (dependencies, access, personal data, configuration). A reviewer the project enabled must pass the changes in its subject before a push.
- `cabinet role add <name>` adds a role of the project's own from as little as its name, asking (or taking as options) what it does, owns, decides and escalates; `cabinet role draft <name>` (`bin/role.sh`), or asking an agent, drafts the whole role for the project as `CABINET.md`, "Drafting a role", says, with its assumptions listed for the owner to confirm. The doctor notes a role not drafted yet (`roles.drafted`).
- A team that changes stays consistent: a whole role of the project's own is used as it is even when the kit has (or later adds) a role with its name, never mixed with it, and the doctor says so (`roles.shadows`); the doctor flags a repo or area with two owners in the team table (`team.single-owner`) and notes open handoffs addressed to no role, repo or owner, such as a role turned off (`handoffs.addressee`).
- Builders: `backend`, `web`, `mobile` and `infrastructure` write the product's code. Each is built when it owns a repo in the team table of `AGENTS.md`; `bin/bootstrap.sh` gives a repo whose owner is `TBD` the builder it most looks like when the repo first arrives. A builder learns how its repo is already built and follows it, tests every change, commits locally and hands finished work to qa (`CABINET.md`, "Builders").
- `guides/` for the project's standing documents (brand, style, policies, business documents), listed in a "Guides" table in `AGENTS.md` that every agent reads; `CABINET.md` ranks guides with `AGENTS.md`, and `bin/doctor.sh` reports a guide with no row and a row with no file. A recipe and a concepts section say where each kind of rule goes and which wins.

### Commands

- One command for everything, named by one set of conventions (`AGENTS.md`, "Command conventions"): one word for the workspace as a whole (`cabinet doctor`, `bootstrap`, `brief`, `move`, ...), and a noun then a verb for what it holds: `cabinet role add|remove|list|draft|build`, `handoff add|attach|record|list|archive`, `repo add|remove|list|snapshot`, `job run|list`, `secret check`, `backup create|verify|restore`. Every command works from any folder inside the workspace or its project, and `cabinet -C <dir>` runs one as if started there. `--json` on every command that reports, `--dry-run` on every command that changes the setup, `--yes` on every command that asks; usage errors exit 2. The workspace scripts use the same words (`bin/<noun>.sh <verb>`), and the tests fail when a command breaks a convention. `cabinet next` says what to do next.
- `cabinet handoff add --from <name> --to <name> --changed "..." --needed "..." "<title>"` (`bin/handoff.sh add`, which `CABINET.md` tells agents to use) files a handoff with the next free ID for today, today's date and the template's lines, and commits it on its own; with someone else's uncommitted lines in `HANDOFFS.md`, it writes the entry but does not commit, so their lines never go into its commit. Entries are filed only with it, never by hand, and a lock left for more than a minute by a writer that was stopped is taken over. `--evidence <file or URL>`, once for each, copies a screenshot, recording or output to `specs/evidence/<ID>/` and links it on the entry's `Evidence:` line, from the workspace root; the brief carries the links to the owner, `archive` rewrites them to open from `handoffs/`, and `cabinet digest` (and `--json`) to full paths. qa never records PASS without evidence that matches what it saw, and blocks the handoff back to its builder instead; the brief does not count a PASS on a handoff with no evidence. Verdicts are one line in one format, `- Verdict: <role> <PASS|BLOCK|CHANGES> <YYYY-MM-DD> <commits> <note>`, and the doctor checks every open entry's verdicts and their notes (`handoffs.verdicts`) and that each qa PASS has evidence (`handoffs.evidence`). `cabinet handoff attach <ID> <file or URL>... --from <name>` lets a handoff's sender add evidence later, and `cabinet handoff record <ID> --role <role> <PASS|BLOCK|CHANGES> --commits <hash,...> --note <file>` writes a verdict in the format and commits it, refusing a note that is not committed, a verdict by the entry's own sender, and a qa PASS on an entry with no evidence; reviewers use only it. New verbs: `attach` and `record`.
- Ready to build (`CABINET.md`): a small task (one repo, no contract change, no owner decision, easy to undo) goes straight to a handoff that says what done looks like; anything bigger is built only from a spec that is ready. `cabinet spec check [spec] [--json]` holds each spec to its status: `ready` needs acceptance criteria, no `TBD` in "Rules", every decision answered, its repos, and a qa PASS on the criteria; `building` also needs each builder's plan under "## Plan" and, for more than one repo, an architect PASS on it. `cabinet spec record <spec> --role qa|architect PASS|BLOCK --note <file>` records those reviews with a fingerprint of the part reviewed, so a later change needs a new review. `cabinet handoff add --spec` routes only a spec that is ready, and builders send back work that is not. The doctor checks every spec (`specs.ready`). New noun: `spec`. A small task is marked: `cabinet handoff add --small` (a `Size: small` line), and work for a repo, a kit builder or a role that owns a repo needs `--small` or `--spec`. `record` refuses a PASS on a small task whose commits span repos, are in no repo on this machine, or change a path `AGENTS.md` guards: a contract's files (`` `<repo>/<path>` `` under "Source of truth") or a new "Hard to undo" list; the doctor flags one already passed (`handoffs.small`). `cabinet config --hard-to-undo "<repo>/<path> ..."|off` sets that list in `AGENTS.md` (adding the section to an older one), refusing a repo not in `repos.tsv` or a path not in the repo; in a terminal it suggests migration folders and `openapi` files found in the repos. The doctor notes a workspace with repos that has not set it (`agents.hard-to-undo`).
- Roles the project adds follow the workflow: "Drafting a role" in `CABINET.md` says a drafted role files handoffs only with `bin/handoff.sh add`, a reviewing role records verdicts with `bin/handoff.sh record` and keeps its notes under `specs/`, and a role that owns a repo is a builder (ready work only, a plan in the spec, evidence, sending back what is not ready, `--small` or `--spec`). The doctor notes a drafted project role that misses one of these, such as one drafted before them (`roles.workflow`); `cabinet role draft <role>` redrafts it.
- Roles that do not overlap: one owner for each area, and an area inside another belongs to its own row (the most specific row wins, `CABINET.md`, "Ownership"). The doctor notes a part of a product repo given to another role than the repo's (`team.nested`) and a project role whose "What you may write" reaches another role's area (`roles.writes`). `cabinet role add --owns` refuses a repo or path that is already another role's row, and notes one inside another's area. "When roles disagree" in `CABINET.md`: within a function its lead settles it; across functions, or when whose call it is is unclear, one sign-off item with both views, and neither acts meanwhile. Drafting a role names its neighbours and how a disagreement with each is settled, and `roles.workflow` notes a project role that does not.
- A team that adapts to the project: the kit keeps a small core of roles and ships none for each specialty. Seat signals come from the project as well as the backlog (a surface, an audience or channel, or a goal with no seat looking after it), each with its evidence; a declined seat is recorded in `notes/seats.md` and proposed again only with new evidence. Checks follow the kind of work, not the kind of role: work that changes no repo is recorded with `cabinet handoff record --commits none` (refused for work addressed to a builder), skips the commit checks, and a spec for it names workspace areas in `repos`. design-lead is the product designer: for a spec built in a repo the web or mobile builder owns, `ready` needs its "Design" section (new in the spec template) and a design-lead PASS on it (`cabinet spec record --role design-lead`).
- The manual as a page: `cabinet manual build [--check]` (new noun `manual`, `bin/manual.sh`) writes `OPERATIONS.html` from `OPERATIONS.md`: one self-contained page (nothing fetched, works offline) with a table of contents, a search that narrows it to matching sections, light and dark themes, and tick boxes for `- [ ]` lines, remembered per browser for the day. All Markdown is escaped and only `http(s)`, `mailto`, relative and `#` links link. It is untracked; setup, `cabinet update` and the brief job (a new `AFTER="bin/manual.sh build"` in new workspaces) rebuild it, and the doctor notes when it is behind (`manual.page`).
- Titles and the org page: `cabinet role add --title "..." --name "..." [--function "..."]` (also when turning on a kit role, into its notes) gives a role the title and display name decisions name it by: the sign-off format names each expert by its title where it has one. `role list` (and `--json`: `title`, `display_name`, `function`) shows them. `bin/role.sh build` writes `ORG.md`, the org page: each function with its lead and members, and each role's title, what it does, what it owns, who it reports to, what it covers and its trial; `build --check` and the doctor's `kit.roles` report it when it falls behind. New workspaces track `ORG.md` (an existing workspace adds `!/ORG.md` to its `.gitignore`). `cabinet role draft` points the drafting agent at `.cabinet/rules/seats.md`.
- Critical areas: a project declares, under "Critical areas" in `AGENTS.md` (a new section, empty by default), the parts where a mistake costs more: each area's paths (`<repo>/<path>`, `workspace/...` for the workspace's own files), the reviewers it needs as well as the usual ones, the evidence they must see, and an optional check, a command in `tools/`. Work touches an area by its commits or by its spec's new `areas` field; readiness adds the area's reviewers (`handoff list --json` includes `areas`), `handoff run` runs them, and `handoff record` runs the area's check before such a reviewer's PASS counts, without a shell and within the run's time limit, keeping its output as evidence. The brief names the areas beside each push. `spec check` refuses an undeclared area; the doctor checks every row (`areas.declared`). Commits in the workspace's own files do not count as code for the reviewers code needs.
- `tools/`: the project's own scripts, placed by `new` and `init`, never touched by updates; the manual must name each one (`manual.complete`), and jobs and critical-area checks call them.
- Sub-teams: `cabinet role add <role> --reports-to <lead> [--covers "<builders or repos>"]` adds a role to a lead's sub-team, recorded in a "## Team" section of its role file (`Reports to`, `Covers`, and `Trial until`, 30 days on). On a handoff from work it covers, its verdict counts for its lead's, so readiness names it in the lead's place and `handoff run` runs it; the lead's PASS always counts, and is needed too until the trial ends. `role list` (and `--json`: `reports_to`, `covers`, `trial_until`) shows who reports to whom. The doctor checks each lead is on the team, that no role leads itself round a loop, and that covered names are builders or repos (`team.reports-to`). `.cabinet/rules/seats.md` has "Sub-teams": when to grow one, onboarding and corrections by the lead, the trial, passing work down, and keeping it shallow.
- The scheduled runner: `cabinet config --pipeline off|small|all --pipeline-limit <dollars> --pipeline-time <when>|off` (off by default; asked in `config`) runs `jobs/pipeline.job`, `bin/handoff.sh run --scheduled`: the work the setting allows (small: handoffs filed `--small`; all: those and ready specs), oldest first, never past the limit for one run (checked before each agent; paused work goes on next run) or a spent weekly budget, and never with a runner whose cost cannot be counted. Work stopped for the owner is skipped until the owner runs it by hand. Each run writes `PIPELINE.md` (untracked), which the brief reports under "Pipeline". A job may set `COMMAND` instead of `AGENT` and `PROMPT`. The doctor checks the runner (`pipeline.ready`). `handoff run` and `spec run` exit 3 when paused at a cost limit.
- The pipeline runner from a spec: `cabinet spec run <spec> [--retries <n>] [--dry-run]` takes a ready spec to all its work ready to push: chief-of-staff routes it, each builder writes its plan, architect reviews the plan when more than one repo builds it, then each of its handoffs runs in the order routing set, as `handoff run` runs one. It stops at the first step that does not finish, and a run again redoes nothing done; it ends with what all its runs cost. `spec check --json` adds `repos`, `missing_plans` and `plan_review`. Readiness also reads the archives, so work closed and archived while its review is open is still found, and a review handoff is never taken for another builder's work that depends on it.
- The pipeline runner: `cabinet handoff run <ID> [--retries <n>] [--dry-run]` moves one piece of work (a handoff to one builder, filed `--small` or `--spec`) through build, review and fixes, an agent run per step: the builder builds and hands on with `--depends-on <ID>`, each reviewer missing or stale verifies, a BLOCK goes back to the builder and its reviewer checks again, up to `--retries` rounds (default 2). It stops when the work is ready to push (saying what it cost), when an agent fails, hits its time limit or leaves no trace, or when the work is sent back; it decides nothing. Runs are logged in `run-<ID>.log` and recorded in the spend file under the work's ID; `handoff list --json` includes `cost_usd`, `depends_on`, `small` and `spec`. Builders hand on for review with `--depends-on` the work's ID. Jobs and the runner share one time limit for an agent run (`run_limited` in `bin/lib.sh`), which prints no "Terminated" line.
- Readiness is computed: `cabinet handoff list --json` gives each entry its `verdicts`, the reviewers it `needs` (each one it is addressed to; for code, qa, security and code-reviewer, and design-lead for a web or mobile builder, each when on the team), and which are `missing`, `blocking` or `stale` (a PASS that does not cover every commit a verdict names, as after a fix), with `ready`; `cabinet handoff list --ready` lists the work ready to push, and the brief asks the owner to push only that. A verdict written outside a Verdict line is reported (`unread_verdicts`; the doctor's `handoffs.unread-verdicts`), never counted. Reviewers name every commit of the work and leave the status alone; chief-of-staff closes an entry once its work is pushed.
- `CABINET.md` holds only what every session needs (about 3,000 words): the detail only some roles or tasks need is in `.cabinet/rules/` (`builders.md`, `ready-to-build.md`, `reviews.md`, `seats.md`, from the kit's `core/rules/`), installed and updated like the other kit files. `CABINET.md` keeps a short form of each rule and a table of when to read each file, and every role names the files its job needs.
- code-reviewer is on by default when setup starts with product repos (`--repo`, `init` in a project, or a folder of repos): qa checks behaviour and security risk, and nothing else reviews the code itself, a gap an owner who does not read code would never see. A workspace with repos and no code-reviewer gets it proposed as a seat, once, unless the owner declined it. The spec template has "## Plan" and "## Reviews".
- `cabinet digest`: one morning read with the sign-off queue and the owner's actions from the latest brief of every workspace on this machine. `--write <file>` writes it to a file, `--notify` sends a desktop notification with the counts, and `--schedule [<when>]` (default every day at 10:00 AM; or another time, or chosen days and a time; `off` to stop) runs it as one launchd job for the whole machine. The chief-of-staff role writes the brief's parts under fixed `## ` headings so the digest can find them.
- `cabinet list`: every workspace on this machine in one table (kit version, what waits on the owner, the doctor's count, the latest brief).
- `bin/doctor.sh` leads with a summary of what needs attention, and `--fix` runs the fixes it knows (asking first).
- One command table in `bin/cabinet` drives `cabinet help`, `cabinet <command> --help`, `cabinet help --json` (every command and option, for agents) and tab completion (`cabinet completion bash|zsh`: commands, options, and job names for `cabinet run`).
- JSON for agents and scripts: `--json` for `status`, `doctor`, `next`, `handoffs [name]`, `digest` and `list`; every doctor result carries a stable check ID, listed in the troubleshooting docs.
- Dates people read (backup age, brief time, restore) are written as `18 Oct 2026, 2:30 PM`.

### Schedules

- macOS and Linux: schedules are launchd jobs on macOS and systemd user timers on Linux, or one block of the crontab where the machine did not boot with systemd (every other crontab line is kept); logs go to `~/.local/state/cabinet/<slug>/` on Linux; the backup passphrase comes from the secret store (`secret-tool`) on Linux, and the doctor also accepts `CABINET_BACKUP_PASSPHRASE`; where cron runs the schedules, a cron run reaches neither the secret store nor systemd's environment, so the passphrase lives in a file only the user can read (`~/.config/cabinet/passphrases/cabinet.<slug>.backup`, written by the command bootstrap prints), and a cron-scheduled backup runs unattended; the file, when it exists, comes first on any machine, one others can read is never used, and the doctor says so (`backups.passphrase`); messages, help and docs say "this machine", not "this Mac" (so `cabinet config --this-machine`), and `digest --notify` shows a desktop notification on both; notifications use `notify-send`; paths under the home folder show as `~/` with bash 5 too. `bin/platform.sh` holds every difference, and `CABINET_SCHEDULER` overrides the scheduler it finds. The doctor reports a Linux machine with no scheduler (`schedules.scheduler`). The test suite runs on both (`npm run test:linux` runs it in a Debian container), and a workspace on a systemd Linux ran its brief and backup on schedule with the doctor all green.
- Jobs as `jobs/<job>.job`, scheduled daily or weekly. A run is stopped, with everything it started, after its time limit: `TIMEOUT` minutes in the job file, else `CABINET_JOB_TIMEOUT` in `cabinet.env` (default 60; `0` for none), with the reason in the job's log. `bin/bootstrap.sh` adds, updates or removes each schedule to match `jobs/` and the backup setting.
- Quiet days: a scheduled run of a job with `QUIET_DAYS` starts no agent when nothing changed since its last full run (no commit, branch or fetch in the workspace or a repo, no new doctor problem, the result file as that run left it), never with uncommitted work or a `default` item waiting in the sign-off queue, and for at most that many days in a row. New workspaces get `QUIET_DAYS="6"` in `jobs/brief.job` (an existing workspace adds that line by hand: the file is the project's), so a quiet workspace costs one agent run a week instead of seven. A run by hand always runs.
- What agent runs cost: with the `claude` runner, each scheduled job and role draft records the cost Claude Code reports (`--output-format json`, `total_cost_usd`) in `spend.tsv` in the log folder; the job's log ends each run with its cost and the week's (`under $0.01` for a run that rounds to nothing), and `cabinet job list` (and `--json`, `cost_this_week_usd`) shows each job's cost this week. Setup and `cabinet config` ask for a weekly budget (`--budget <dollars>|off` on `new`, `init` and `config`; `CABINET_BUDGET`); the doctor warns from 80% and when it is passed (`spend.budget`), and notes a budget the runner cannot track (`spend.unreported`). The week starts on the day `AGENTS.md` names. Every built-in runner is counted: claude, grok and opencode report dollars; codex, cursor, qwen and antigravity report tokens, priced with `--price "<input> <output> [<cached input>]"` (`CABINET_PRICE`, dollars per million tokens), which setup asks for after the budget; `spend.tsv` also keeps the tokens. Each runner prints JSON, read for the reply and the cost; output that is not that JSON reaches the log as it is. Nothing is stopped by the budget. `cabinet digest` shows each project's spend this week against its budget (`--json`: `spend_this_week_usd`, `budget_usd`), counts projects at 80% of their budget or more, and gives the total across projects.
- One form for every schedule (the brief, any job, the backup time, the digest): 12-hour times (`7 AM`, `4:30 PM`), every day or on days, one or several (`fri 4 PM`, `sun,mon,tue,wed,thu 8 AM`), with days by short or full name in any case. Times are stored and shown as `4:00 PM`; 24-hour times are still read.
- Scheduled runners: claude, codex, antigravity (`agy`, run with `--dangerously-skip-permissions`, since headless Antigravity denies what it cannot ask), qwen, grok, opencode, cursor, and `custom` for any other tool (`CABINET_RUNNER_CMD`). Gemini CLI is not a runner (Google moved its users to Antigravity): a workspace set to `gemini` is told to run `cabinet config --runner antigravity`. Gemini CLI keeps its guardrails.
- `cabinet bootstrap --no-schedules` (and `--schedules` to undo it): a machine that should not run the workspace's jobs, such as a teammate's in a shared workspace, skips their schedules from then on; the choice is saved in `cabinet.local.env`, which git never tracks.

### Guardrails and safety

- Agents are denied reading the backup passphrase from the Linux secret store (`secret-tool lookup` and `search`), as from the macOS keychain, in every tool's rules, and any shell command naming the passphrase file's folder in Claude Code, Grok, Qwen Code, opencode and Gemini CLI.
- Guardrails for Claude Code, Codex, Antigravity, Gemini CLI, Qwen Code, opencode and the Cursor CLI (Grok reads the Claude Code rules; the Cursor rule shapes were probed live on Cursor CLI 2026.10.16), checked by `bin/doctor.sh` (opencode on 1.x only), which also names installed tools it cannot guard; and the owner's pre-push gate for every tool.
- Values from a cloned project's `package.json` never reach a shell (only plain values are used, the description is quoted as data); clone URLs and repo names are checked; a slug another workspace uses is refused.
- Backups must live outside the workspace and its repos, clean up only their own archives, and restore never loses a file. `cabinet backup verify` restores the newest archive into a temporary folder, checks the workspace and each repo against it (a damaged or incomplete archive fails), and deletes the copy; the doctor notes when no restore has been verified in 92 days (`backups.verified`).
- Config files keep their permissions and symlinks, and a file that is not plain JSON, or holds a value a rewrite would change (`1.0`, `1e3`, a number too large to keep exactly, a key that is a whole number), is left alone; a byte-order mark before the JSON is accepted; every git hook passes through to the repo's own under the global hooks path.
- A secrets check: `cabinet secret check` (`bin/secret.sh check`) looks for keys, tokens and passwords in the workspace's files and names each file and line, never the value; the doctor runs it (`secrets.none`), bootstrap places a pre-commit hook in the workspace that refuses a commit adding one (`secrets.hook`), and `not-a-secret` on a line marks a false alarm.

### Docs

- For people: a short README with a quick start, the daily loop and a glossary; a tutorial for the first day and a recipes page for common tasks; `docs/` with the full command reference, layouts, concepts, guardrails, backups and every doctor message.
- For agents: `llms.txt`, `llms-full.txt` with every page in one file, and `AGENTS.md` for working on the kit.
- `brand/index.html`, the brand guide: the idea behind the mark (and when the table may appear: in pictures that explain it, never in the logo), its forms, sizes and clear space, when the open seat is outlined in brass (and when it may appear on hover), the loading animation (the seats lit one at a time around the table, the open place a rest beat, ending on the mark), the logo in motion (the owner's outline in the middle, the team fanning out of it to the table, the owner moving to the open place, then the name) and ten variants for other uses, shown moving in `brand/motion.html`, the chairs (an illustration of the mark for animation, onboarding and large pictures, never the logo; in motion, like the logo animation, they start with the owner in the middle), the name, color and the status colors for ok, note and fix, type, writing, where each form goes, and every logo file as SVG. Kept in the repository, not shipped in the package.
- The brand as files: `brand/BRAND.md` (every rule in plain text with its status, approved or draft, ready to copy into a workspace's `guides/`), `brand/tokens.json` (colors, status colors, fonts, the mark's geometry), and `brand/assets/` (the mark, the name and lockups as outlines, favicons, app icons, the chairs and the social preview, as SVG and PNG), built by `tools/build-brand.py` (`npm run brand`). `npm test` fails when a file is out of date. The promo film in `brand/promo/`: 32 seconds cut to its music, ending on the repository's address or on what Cabinet is, with its source and its Suno prompt. The demo film in `brand/demo/`: 94 seconds from an empty folder to the first morning, in seven chapters, with every command's real output captured in a sandbox and the agent's part shown as labeled examples. `brand/render-film.js` renders either film again. Not shipped in the package.
- For contributors: `CONTRIBUTING.md` (where questions, bugs and security problems go, the rules reviews check most, the checks to run, working with an agent, pull requests), `SECURITY.md` (private reports through GitHub, what counts), `CODE_OF_CONDUCT.md` (the Contributor Covenant 2.1 and where to report), issue forms for a bug, an idea and support for an agent tool, with blank issues off and questions sent to Discussions, and a pull request template. The README links them. Kept in the repository, not shipped in the package.
- Installed from npm first: the README, the setup guide for agents and the tutorial no longer skip `npm install`; the clone install stays for the newest code, with how to move from a clone to the package.
- Credit and rights: a `NOTICE` file (shipped in the package) that anyone redistributing Cabinet or building on it must keep, under the Apache License; `brand/LICENSE.md`, which keeps the name, logo, brand guide and films out of the code's license; the README's License section says both, and `package.json` names the author with a link.
- The tests fail when the docs fall behind the code, a link or heading anchor is broken, `llms-full.txt` is stale, the README's clone command does not match the repository in `package.json`, a local path is left in the kit (the brand demo's made-up `/Users/maya` is allowed), or, with `CABINET_PRIVATE_WORDS` set, one of those words appears as a whole word anywhere in the kit.
