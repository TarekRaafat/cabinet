# Roadmap

What cabinet does next, in order. Each item says what is missing today, what it takes, and when it counts as done. Items move to `CHANGELOG.md` when they ship.

**One rule for every item:** cabinet is shaped by the people who use it, not built around one kind of project. It has to fit any product (a web app, a mobile app, a library, a service, client work, a business with little code), any team (one person to a small company, people and agents in any mix) and any experience (new to everything, or expert in some areas). So every item below is optional, turned on and tuned per project in its own settings, and has a sensible default for a project that does not care; nothing assumes a number of repos, a stack, a market, an outside service or a way of working. Where an item needs project-specific detail (what is critical, which contracts exist, what a release is), the project declares it, and the kit supplies the mechanism, not the content.

## 1. Full Linux support

Today cabinet is built and tested on macOS. On Linux the team files, setup and guardrails should work but have never run there, and four parts are macOS only.

- **Schedules:** setup installs, updates and removes systemd user timers (cron where systemd is absent), the same way it handles launchd on macOS. Today setup installs nothing on Linux and says to use cron by hand.
- **Backup passphrase:** read from the Linux secret store (`secret-tool`) or `CABINET_BACKUP_PASSPHRASE`. The health check accepts either; today it always reports the passphrase missing on Linux.
- **Dates and paths:** the health check computes the backup's age with GNU `date` too (today it uses a macOS-only option), and logs go to `~/.local/state/cabinet/<slug>/` on Linux.
- **Tests:** the suite runs on Linux (today it uses the macOS form of `sed -i`), and passes in a Linux container.
- **Install:** `package.json` adds `linux` to `os` (today npm refuses to install on Linux), and the README's platform line says so.

Done when: the full test suite passes on macOS and in a Linux container, and a workspace on Linux runs its brief and backup on schedule with `bin/doctor.sh` all green.

## 2. Windows support, through WSL

Windows runs cabinet through WSL (Windows Subsystem for Linux), which gives the Linux support above. Native Windows (PowerShell, or Git Bash, which lacks `jq` and other tools the scripts use) is not a goal.

- A README section: installing WSL, where the workspace should live (the WSL file system, not a mounted Windows drive, for git speed and file permissions), and running the agent tools inside WSL.
- The guardrails for agent tools installed inside WSL; a note on tools installed on the Windows side, which those guardrails do not cover.
- The test suite run under WSL once.

Done when: the full test suite passes under WSL, and the README walks a Windows user from nothing to a working workspace.

## For founders without every skill

The goal: cabinet is equally useful to a founder with no technical or business background and to one who is expert in one area (engineering, design, sales) and lacks the rest, and equally useful for a project that is only an idea and for an established one with code, users, a team and its own ways of working. The team fills what the founder lacks, explains what the founder must decide in the founder's terms, and stays out of the way where the founder is the expert. Today the kit is strong at governance (who decides, independent review, guardrails, the daily sign-off) but assumes the founder knows how to build and run a product. Items marked **pick first** come before the rest. Every item works for both kinds of project: for an established one it learns what is there and follows it, and it never replaces the project's stack, conventions or rules with defaults.

- **The founder's profile.** Ties the items below together. At setup (and with `cabinet config`), the founder says what they know well and what they do not, area by area: engineering, design, product, marketing, finance, legal and admin. Every role reads it: where the founder is expert, agents bring fewer and more technical decisions and skip the explanations; where the founder is new, they explain more, bring the choices pre-made with a recommendation, and say when a professional is needed. Done when: the same decision reaches an expert founder as a short technical choice and a new founder as a plain question with the trade-offs explained, from one profile setting.
- **Builder roles** (pick first). Today all seven kit roles plan, review, coordinate or price; none writes the code, and each product repo's owning agent starts as `TBD` with no role definition. Builder roles (backend, web, mobile, infrastructure), each owning its repos, with how to test and when to hand to qa already written, assigned when a repo is added. In an existing repo the role learns and follows what is there: the stack, the test, lint and build commands, the CI, the code style and the repo's own `AGENTS.md`; defaults apply only to a new repo. Done when: a founder who adds a repo, new or years old, gets an agent that can build in it the way that repo is built, with no role written by hand.
- **From an idea to a plan** (pick first). Today the kit starts once a product exists, with `TBD` lines in `AGENTS.md` to fill. A kickoff, run once at setup or any time after, in one of two modes. For a new idea, the product-manager interviews the founder (the problem, who has it, what is in and out of the first version, how success is measured). For an established project, the team first learns what exists (the code, the docs, the git history, the open issues, how it is built, tested and deployed) and asks the founder only what none of that tells. Either way it writes `AGENTS.md`, the specs and a roadmap (for an established project, the current state and what is next), each marked for the founder to confirm. Done when: a founder with only an idea, or with a running product, ends the kickoff with no `TBD` in "What the project is" and "Product rules", and a ranked roadmap that starts from where the project really is.
- **See the result, not only the verdict** (pick first). Today qa records PASS or BLOCK, and a founder who cannot read code approves on trust. Each finished handoff carries evidence the founder can check without code: screenshots, a short recording, a link to try it, or the command output for work with no screen. qa refuses a PASS without it. Done when: every handoff that reaches the founder for sign-off shows what was built.
- **Guard the founder's time and money** (pick first). Today nothing tracks what the agents cost, and the sign-off queue has no limit. AI spend per workspace (what the scheduled runs and sessions cost this week, from what each tool reports), with a budget and a warning before it is passed; and a daily cap on the sign-off queue (for example five decisions, ranked; the rest wait, and the brief says how many), since for a solo founder the queue is the bottleneck. Done when: the founder sees the week's spend and is warned before a budget is passed, and no brief asks more decisions than the cap.
- **Setup without terminal skills.** Today setup needs git, jq and Node.js, quoted options and terms like launchd. One install command that checks every prerequisite and installs what is missing, asking first; messages in plain language, with the technical detail one step away; and `cabinet next` steps that say why each matters. Done when: a founder who has never used a terminal reaches a working workspace by following the screen.
- **Decisions that do not assume expertise.** Today a founder can be asked to pick a database, a host or a payments provider without knowing the trade-offs. Starter stacks, for new projects only: one recommended, well-supported stack for each kind of product, so the first technical choices are made and can be changed later (an established project keeps its stack). And in every technical decision, new or established, what each option costs and what changing it later would take. Done when: a new project's first technical choices arrive made, an established project's stack is never replaced by a starter, and each technical decision shows cost and the cost of changing course.
- **After launch: running, customers and growth.** Today no role covers production or customers. Roles turned on when the product goes live, or at setup for one already live, using what it already has (its hosting, monitoring, support inbox and analytics) before suggesting anything new: reliability (deploys, monitoring, an incident checklist, rollback, a status note for users), support (feedback and support replies, turned into specs) and growth (a landing page, launch posts, finding the first users, and regular posts about the work for founders who build in public, drafted for the owner to approve). Done when: a live product has an owner for incidents, for customers and for growth, each with its checklist.
- **Business basics.** Today nothing tracks the business side a founder without advisors misses: forming a company, a privacy policy and terms, taxes and invoicing, app store rules. A checklist role that tracks these, reminds at the right moment and says when to get a professional; its definition forbids legal or tax advice of its own. Done when: a workspace shows which basics are done, open or need a professional, and the role never gives a legal or tax answer itself.
- **People and agents side by side.** Today every repo or area has an owning agent. An established team has people who own parts of it. Each repo or area is owned by an agent, by a person, or shared: where a person owns it, agents read and propose (a branch, a patch or a handoff with the change) and the person reviews and decides; the team table and the brief say which is which. Done when: no agent changes a person-owned area except by a proposal that person accepts.
- **Work the team's way.** Today agents commit locally and the owner pushes. A team may work through branches, pull requests, required reviews and CI. Agents follow the project's own workflow (branch names, commit style, opening a pull request for review where the team does) while push, merge and release stay with people, as the guardrails already make sure. Done when: in a project that works by pull requests, every agent change arrives as one, and nothing merges without a person.
- **The existing backlog** (needs the owner's decision first: it reads an outside service). An established project's open issues and roadmap live in its tracker. A one-time import, then a regular read, turns them into specs and handoffs with links back, without changing the tracker. Done when: the team's open work appears in the workspace, each item linked to its source, and nothing is written to the tracker.
- **Learn by example.** Today the templates show the format, full of `TBD`. A filled example workspace for a made-up product (a finished `AGENTS.md`, real-looking handoffs, a brief with its sign-off queue, a spec, a guide), shipped in the docs and kept in step with the templates by the tests. Done when: every template file has a filled counterpart in the example, and the tests fail when they drift apart.

## Running the work

Patterns proven in daily use of an agent team, made general. Each is optional and declared by the project; items marked **pick first** come before the rest.

- **A pipeline runner** (pick first). Today the owner or chief-of-staff starts each next agent by hand, which is the bottleneck for a founder without people. A runner moves one piece of work through the steps the project already has (spec ready, the owning agent builds, the reviewers the project enabled verify, fixes after a BLOCK, a re-check) and stops when the work is ready for the owner to push; tiers and sign-off do not change, and the runner decides nothing itself. The project sets which steps apply, how many times a repeated BLOCK is retried before it stops and asks, and whether it runs on demand or on a schedule. Adding it changes what runs unattended, so turning it on is the owner's decision. Done when: a ready spec reaches "ready to push" with no agent started by hand, and stops to ask after the set number of BLOCKs.
- **Stricter checks for what must not break** (pick first). Today `AGENTS.md` has one `TBD` line for "what needs a stricter gate". The project declares its critical areas, whatever they are for it (payments, data import, anything with personal data, a public API, a release to an app store), and for each: the extra verdicts required, the evidence required (for example replaying a saved set of real inputs and comparing every result, or a load test), and, for an area that calls an outside service, a request budget that a change may not raise without the owner. qa refuses a PASS without them, and the brief shows which pending work touches a critical area. Done when: a change in a declared area cannot reach "ready to push" without its declared verdicts and evidence.
- **A capability inventory** (pick first). Today nothing records what the product can actually do. A living list, read from the code (and from the docs for a product with little code): every capability, its status (live, built but not released, behind a flag, planned), where it lives, and what it depends on, re-checked against the code by an agent and verified by qa. It is the base for the roadmap, pricing and plans, and the first thing the kickoff writes for an established project. Done when: every capability the code has is in the list, and a re-check reports any that were added, changed or removed.
- **Push deploys, said plainly** (pick first). Today nothing marks a repo where pushing goes live. A column in `repos.tsv` says what a push does (nothing, deploys a preview, deploys to production, publishes a release), and the brief, the digest and the sign-off queue say so beside every push the owner is asked for: "pushing this goes live". Done when: every push request for a repo marked as deploying says it is a live deploy.
- **Checks on contracts between repos.** Today the contracts table names each contract and its source of truth, and nothing verifies them. A contract can name its check (a script, a schema comparison, a test), run by the doctor and by qa before a push; a change on one side that breaks the other is caught then, not by users. Done when: a declared contract with a check fails the review of a change that breaks it.
- **One writer for shared outputs.** Today two agents can work in the same repo copy and collide. A project can name a repo or area with a single writer (a docs site, a website, a release): the others write their part in their own repos and hand it off, and only the writer commits there. Done when: in a single-writer area, every commit comes from its writer, and the others' content arrives through handoffs.
- **Names for the team, and an org page.** Today roles are named by their file (`product-manager`). A project can give each role a title and a display name (for example "Head of Product"), used wherever decisions name each expert's recommendation; and a page generated from the roles and the team table shows who owns what, decides what and reports to whom, for the founder, for people joining, or for a public team page the owner approves. Done when: every decision in the queue names its experts by their titles, and the page rebuilds from the roles on every change.
- **A market watch job.** Today nothing keeps an eye on the market. An optional weekly job tracks what the project names: other products, prices, launches, reviews, rules in its industry, and reports what changed since last week, for the team only. Done when: a project that turns it on gets a weekly report of changes, and nothing from it reaches anything published.
- **A readable manual.** Today the owner's manual is Markdown. It is also built as a formatted page (contents, links, search), rebuilt whenever `OPERATIONS.md` changes, and the doctor says when the page is behind. Done when: the page always matches the Markdown.

## Ideas to pick from

Not ranked yet; each is picked and ordered when its implementation starts.

### Safety

- **A secrets check.** Today nothing stops a key, token or password pasted into a note, guide or handoff from being committed and copied into every backup. `cabinet doctor` and a pre-commit hook in the workspace look for them (common key formats, private key blocks, lines that set a password or token) and refuse the commit, with a way to mark a false alarm. Done when: a test key in a guide is caught before it is committed, and a marked false alarm passes.
- **Backups that test themselves.** Today the docs ask for a restore by hand once a quarter. `cabinet backup --verify` restores the newest archive into a temporary folder, compares it with the workspace and its repos, reports any difference, and deletes the copy; the doctor says when the last verified restore is too old. Done when: a damaged or incomplete archive is reported by `--verify`, and a good one passes.

### The daily loop

- **Answer from the digest.** Today `cabinet digest` gathers every sign-off queue, but each answer still means going into that workspace. `cabinet answer <workspace> "1: approve; 2: no"` delivers the answers to that workspace, where its chief-of-staff applies them on its next run, as if given there. Done when: answers given from anywhere reach the right workspace once, are applied there, and the next digest no longer lists them.
- **A decisions log.** Today the owner's answers are applied into specs and handoffs, so "what did I decide about X, and when" means searching several files. Each answer is recorded with its date, the question and the outcome in one file per workspace, and `cabinet decisions [word]` searches it. Done when: every applied answer has its entry, and a search by word finds it.
- **A weekly review job.** Today the daily brief looks at today. An optional job, on the day the week starts, sums up the week: what shipped, which handoffs closed, which decisions were made, what is stuck and for how long, and how that compares with the week before. Done when: a workspace can turn it on in setup or config, and it runs on the week's first day.
- **Run history and failure alerts.** Today a failed scheduled run shows only as a late brief the next day. `cabinet runs` lists each job's recent runs (when, how long, success or failure, from the job logs), and a failed scheduled run, or one stopped by its time limit, can send a notification and is named in the next brief. Done when: a failing job is reported the same morning, and `cabinet runs` shows its last runs.

### Control

- **Pause and resume.** Today stopping the schedules for a holiday, a trip or a project on hold means turning them off one by one and setting them up again. `cabinet pause [until <date>]` stops every schedule of one workspace, or of all of them with `--all`, and `cabinet resume` (or the date passing) brings them back exactly as they were; `cabinet list`, the digest and the doctor show a paused workspace as paused, not broken. Done when: pause and resume leave every schedule as it was, and a pause with a date ends on its own.
- **Guardrails status and removal.** Today the guardrails are checked per workspace by the doctor, and removed by hand from each tool's settings. `cabinet guardrails` shows, for every agent tool on the Mac, which of the kit's rules are in place, and `cabinet guardrails remove` takes out exactly what cabinet added (from the backups bootstrap made, or rule by rule), leaving the owner's own rules. Done when: after `remove`, each tool's settings match what they were before the first bootstrap, apart from the owner's later changes.

### Starting and working

- **Choose the model, and check it exists.** Today cabinet chooses only the agent tool (`CABINET_RUNNER`); every scheduled job runs with that tool's default model, and the only way to name a model is a custom runner command, which nothing checks and which loses what the built-in runners pass (such as the named role). A `--model` setting for the workspace (`CABINET_MODEL`) and an optional `MODEL=` per job file (one model for the brief, another for heavier jobs), passed through each tool's own model option. The check: where a tool can list its models without a paid call, setup, config and `cabinet doctor` confirm the model is there; where it cannot, an explicit opt-in check makes one short real call, since that costs a little. Each tool's model option and listing command is confirmed live before the kit relies on it, as the Cursor rules were. Done when: a mistyped model is caught before the first scheduled run in every tool that can tell, and the docs say for each tool which kind of check it gets.

- **`cabinet start <role>`.** Today a session as a role is set up by hand in the agent tool. `cabinet start qa` opens the configured agent tool in the workspace with that role's definition and its open handoffs loaded, for every tool cabinet supports. Done when: one command starts a working session as any enabled role, in each supported tool.
- **Presets for kinds of project.** Today every new workspace starts from the same templates, with many `TBD` lines. `cabinet new --preset <kind>` (for example a web product, a mobile app, a library, client work) adds starter product rules, guides, roles and jobs that fit. Done when: a preset leaves fewer `TBD` lines than plain setup, and a project can still change everything it added.
- **Adopt an existing agent setup.** Today a workspace built by hand (its own `AGENTS.md`, handoff log, role definitions, notes) can only be rebuilt from scratch. `cabinet adopt` maps what it finds onto cabinet's files, keeping the content and history, and lists what it could not map. Done when: a hand-built workspace becomes a cabinet workspace without losing a file, and `cabinet doctor` passes on it.

### Teams

- **A shared library of roles and guides.** Today a role or guide written for one project is copied by hand into the next. `cabinet add role <git url | workspace>` (and `cabinet add guide`) installs it, records where it came from, and updates it the way the kit updates, never over a local edit. Done when: a team keeps one copy of a role or guide and every project that uses it can take its updates.
- **`cabinet update --dry-run`.** Today an update applies at once and stops only on an edited kit file. The dry run lists every kit file the update would change, with the diff, and the changelog it would show, and writes nothing. Done when: the dry run predicts exactly what the update then does.

### Needing the owner's decision first

These send data out of the machine or depend on outside services, so each starts as a decision for the owner.

- **Digest notifications by email, Slack or Telegram**, for owners away from the Mac.
- **A CI check for shared workspaces**, verifying the handoff log, the built roles and the guides table on every pull request.

## Later, when a project needs it

- **Hardening found in review:** archives use AES-256-CBC without a MAC (tampering shows only as a tar or gzip error); the keychain item can be read without a prompt by any process of the user (deny rules stop agents in the guarded tools; creating the item to always ask would need a decision for scheduled backups); opencode agent-level and project-level configs, and Qwen workspace settings, can loosen the global rules (`bin/doctor.sh` checks only the global result); folder names without Latin letters or digits need `--slug`; on opencode 2.x, `bin/doctor.sh` cannot read the resolved permission rules (its debug commands need opencode's background service), so its guardrails are unverified there.

- **More than one owner:** today the kit assumes one person signs off. Two founders, or a lead per area, each sign off their own decisions: owners named in `AGENTS.md` with what each decides, every sign-off item addressed to one of them, the brief's queue grouped by owner, and the digest showing each person only their own. The push gate and guardrails stay per person. Wait until a team needs it: it is the largest change here. Done when: an item addressed to one owner reaches only that owner, and an owner's answer applies only to their items.
- **One Mac runs the jobs, without asking teammates:** in a shared workspace, a teammate must remember `cabinet bootstrap --no-schedules`, or their Mac schedules the brief too and the team gets two. A choice to study: record in the shared `cabinet.env` which Mac runs the jobs (filled at setup with the owner's Mac), so bootstrap on any other Mac skips schedules on its own and names the Mac that runs them, while `--schedules` still lets a Mac take over. Open questions: how to tell Macs apart (the computer name changes when a Mac is renamed, which would stop its schedules until re-recorded), what the doctor reports on each side, and how a handover works when the owner's Mac is gone. Done when: a teammate who clones a shared workspace and runs a plain `cabinet bootstrap` schedules nothing, and the owner's Mac keeps its schedules.
- **Projects in other languages:** `cabinet init` reads `pyproject.toml`, `Cargo.toml`, `go.mod` and `composer.json` for the name, description and test commands, as it reads `package.json` today.
- **Install without Node.js:** `git clone` and one symlink, with the version pin kept as a git tag in `cabinet/.cabinet/` and read by `cabinet update`. The npm package stays the main route.
