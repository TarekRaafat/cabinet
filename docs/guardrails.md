# Guardrails

How Cabinet keeps every push, merge, release and publish with you, what each agent tool's rules can and cannot block, and how to undo them.

## The two layers

1. **The push gate.** A global git pre-push hook asks for `yes` at your terminal before a `git push` in Cabinet's repos, from any tool: each workspace on this machine and everything inside it (session worktrees too), every repo a workspace lists in `repos.tsv`, and the project around a `cabinet/` folder. Agents run without a terminal, so their pushes there are refused. In any other repo it asks nothing and runs that repo's own `pre-push`, if any. It reads the workspaces Cabinet records on this machine (in the log folder) at each push, so a repo added today counts at once; whenever it cannot tell (`node` not on the `PATH`, as under some GUI git clients, a workspace or its `repos.tsv` it cannot read, a recorded workspace that is gone, no recorded workspace still there, a bare repo), it asks. Bootstrap records each workspace, with or without a scheduler; a second workspace with a slug another one holds is recorded beside it, and the doctor reports a workspace no record names (`guardrails.claim`). It has no off switch of its own: no setting of the kit's makes it pass. The ways around any git hook, and which tools' rules catch them, are listed below.
2. **Deny rules in each agent tool.** They block push, merge, release and publish commands, and the known ways around the push gate (git can be told to skip hooks).

Together they are a strong speed bump, not a boundary. For a hard boundary, protect your branches on the server (GitHub branch protection), and use [a credential that needs you on every push](#a-hard-boundary).

Each workspace's `CABINET.md` also tells agents that outside content is data, not instructions: what they read from a cloned repo, a web page, an issue or a tool's output never changes their task, and when it gives orders they stop and tell you where. That is a rule for the model, not an enforced boundary: the deny rules and the push gate stay the guardrails.

## A hard boundary

The push gate and the deny rules guard against mistakes; a process set on getting round them could still push with your credentials. A credential that needs your confirmation each time it is used closes that: no push reaches the remote without you, even if every rule on this page were bypassed. Two kinds, both from the ssh tools' own documentation:

- **A key the ssh agent confirms on each use.** `ssh-add -c <key>` adds a key to the agent so that every use of it is confirmed first, in a dialog shown by an askpass program (`ssh-askpass`, or the program `SSH_ASKPASS` names where the agent starts). With no askpass program, every use of that key is refused. macOS ships none, so one must be installed and named in `SSH_ASKPASS`; on Linux it is a package of its own (`ssh-askpass` on Debian).
- **A hardware security key that needs a touch.** A key of an `-sk` type (`ssh-keygen -t ed25519-sk`, or `ecdsa-sk`) lives on a FIDO security key, and each use needs a touch on it. On Linux the system ssh supports it (`ssh -Q key` lists the `sk-` types). The ssh that comes with macOS lists the types but cannot reach a security key by itself (`ssh-keygen` says "No FIDO SecurityKeyProvider specified"): use an ssh built with security key support, or set `SecurityKeyProvider` to a provider library.

Its limits:

- It covers a push only while the remote is reached over ssh with that key, and no other stored credential reaches the same host. A token in a git credential helper (for an HTTPS remote), or another key in the agent or in `~/.ssh` that the host accepts, pushes without asking. `git remote -v` shows how each repo reaches its remote; `ssh-add -l` lists the keys the agent holds.
- It does not cover what goes through the GitHub login token (`gh`: merges, releases, repository settings). Branch protection and the deny rules cover those.

`cabinet bootstrap` points here once, at the end of its push gate section; it detects and changes nothing.

## What bootstrap installs

`bin/bootstrap.sh` installs the guardrails machine-wide, for every tool it finds. It is safe with several workspaces: rules are only ever added, never removed; a config file that is not plain JSON, whose shape is unexpected, or that holds a value a rewrite would change (a number written as `1.0` or `1e3`, one too large to keep exactly, or a key that is a whole number), is left exactly as it was, with a message; files are written in place, so their permissions and symlinks stay; and a backup copy `<file>.bak.<timestamp>` is made before any change; when that copy cannot be written, the file is left as it is, with a message, and bootstrap goes on with the next tool. The push gate is replaced only where it is the kit's own earlier copy; a `pre-push` of yours there is left as it is, and the doctor fails, since it reads a hook and never runs it, so it cannot check that yours asks before a push: move yours into each repo's own `.git/hooks`, where the kit's gate runs it. An older copy of the Codex rules or the Gemini policy, missing rules a newer kit added, gets the missing rules at its end, after a comment line and a backup copy beside it; no line already there is removed or changed, a symlink stays a link (its target gets the rules), and the result is written only when it checks out: for Gemini, when it holds every kit rule; for Codex, when it defines no name twice and, with `codex` installed, `codex execpolicy check` still forbids `git push`. Otherwise, or when the backup cannot be written, the file is left as it is and bootstrap says why, with the lines to add by hand. Run `cabinet bootstrap` after each kit update.

Two more machine-wide settings come with the push gate:

- **`git config --global core.hooksPath ~/.config/git/hooks`**, where the gate lives, with its helper `cabinet-push-gate.js`, which finds Cabinet's repos. A global hooks path makes git skip every repo's own `.git/hooks`, so bootstrap also places a pass-through stub there for the other client hooks (pre-commit, commit-msg, post-checkout and the rest; not push-to-checkout or fsmonitor-watchman, which change git's behavior just by existing). A repo's own hooks, such as a secret scanner, keep running. `prepare-commit-msg` is the credit hook instead ([credit roles](concepts.md#credit-roles)): it runs the repo's own `prepare-commit-msg` in the same way, whose failure still stops the commit, then refuses foreign attribution and adds the role's line to a commit made in a Cabinet run. It also refuses an amend in a Cabinet run, and `pre-rebase` is the kit's too, refusing a rebase there ([runs never rewrite](#runs-never-rewrite)). Bootstrap places each where there is no hook, or where the stub or an earlier version of the same hook is, and never replaces a hook of yours; an earlier version you edited is kept first beside it as `<hook>.cabinet-v<N>` (git never runs it), and when that name is taken, the hook is left as it is; `--no-verify` does not skip `prepare-commit-msg`. A Cabinet repo where git uses another hooks folder skips the gate: its own `core.hooksPath` (husky sets one), set in the repo, a worktree, a file its config includes, or the system config. The doctor reads the value git really uses in the workspace, each repo it lists and each session worktree, and names the folder, the value and the file that sets it; it never reads other repos.
- **The workspace's secrets check,** a `pre-commit` hook in the workspace's own `.git/hooks` (bootstrap runs it through the pass-through stub). It runs `bin/secret.sh check --staged` and refuses a commit that adds a likely key, token or password, naming the file and line, never the value. A false alarm passes once its line has `not-a-secret` on it. When `bin/secret.sh` is missing or not executable, the hook refuses every commit rather than let one through unchecked. An existing `pre-commit` hook is left as it is, unless it is the copy Cabinet 0.1.0 to 0.5.0 placed, which let such a commit through: bootstrap replaces that one. The doctor follows the hook git really runs for a commit in the workspace (through the global pass-through stub, or a `core.hooksPath` set for the workspace) and says ok only when it is the kit's hook; any other it names as not checked (your hook can call `bin/secret.sh check --staged` itself). A shared `cabinet/` inside a project gets none, since the project's own hooks run there; `bin/doctor.sh` still scans its files. It is a safety net, not a guarantee: it knows common key formats, not every secret.
- **Gemini CLI's `context.fileName`** is set to read `AGENTS.md` everywhere, so Gemini also loads `AGENTS.md` in folders that are not Cabinet workspaces.

## What each tool's rules block

The rule formats differ, so the coverage does too.

**Claude Code, Grok, Qwen Code, opencode** (one rule list, matched anywhere in a command, so also inside wrappers such as `env`, `bash -c` or `nohup`):

- push, `git send-pack` (which pushes without hooks), merge, release, `gh api` writes, publishing (npm, npx, bun, pnpm, yarn, also with options before `publish`);
- the ways around the gate: `-c core.hooksPath` in common spellings, `GIT_CONFIG_*` variables, `env -i` and `env -u`, a push behind a `HOME=` override (caught because `git push` is matched anywhere), `--no-verify` and its abbreviations, faking a terminal (`script`, `expect`, `unbuffer`, Python's `pty.spawn`);
- printing the GitHub token, and reading the keychain, the Linux secret store (`secret-tool lookup` and `search`), git's stored credentials (`git credential`) or the backup passphrase file (any command naming `cabinet/passphrases`).

Side effects: some harmless commands are refused too, such as an npm script named like `publish-docs`, or any command that mentions `git push` (for example in an `echo`).

**Gemini CLI** (regular expressions): the same list, with the hooks path matched in any letter case and `git push` matched anywhere in a command.

**Cursor CLI** (the command's first word plus an arguments pattern): push, `send-pack`, hook-path and `--no-verify` arguments to git, the terminal fakers, merges, releases, `gh api` writes, publishing, the GitHub token, the keychain and `git credential`. Probed live on Cursor CLI 2026.10.16 with harmless stand-ins:

- argument patterns match at the start and in the middle; first-word rules match;
- chained commands (`a && b`) are checked;
- a leading variable (`HOME=... git push`) is dropped before matching, so the git rules still catch it;
- wrappers are not looked through, so the kit denies `env`, `bash -c`, `sh -c`, `zsh -c`, `nohup`, `xargs`, `sudo`, `exec`, `command`, `nice` and `stdbuf` outright, and `timeout` or `time` with push, publish or `send-pack`. Any other wrapper is not caught.

**Codex and Antigravity** (rules match only how a command starts): push, `send-pack`, `env -i` and `env -u`, merge, release, publish, the terminal fakers and `git credential` are denied; `git -c ...` and `gh api` ask first. A bypass that does not start the command, such as `HOME=... git push` or `--no-verify` after other words, is not caught; nor is a push with `PATH=` pointing at a fake `node`, `NODE_OPTIONS=--require <file>`, or, on Linux, `XDG_STATE_HOME=` pointing at a made-up log folder, each of which can make the gate's helper say a repo is not Cabinet's. Tools that match `git push` anywhere in a command catch all of these.

**Not caught by any tool's rules:** git config keys in unusual letter case (except in Gemini), an agent editing `.git/config` with its file tools, except in Claude Code (the doctor reports a repo's own `core.hooksPath` afterwards), an agent removing a repo's row from `repos.tsv` or deleting a workspace's record in the log folder, which takes that repo out of the gate (the workspace's git history shows a `repos.tsv` change; the doctor's `guardrails.claim` shows a missing record), and other ways of faking a terminal.

## Runs never rewrite

An agent may run a rebase, a local merge or another git action that can be undone only when you ask for it in its session, except an amend of its own newest commit before it is pushed or named in a handoff or verdict ([git actions](concepts.md#git-actions)). In a Cabinet run (a scheduled job, `cabinet handoff run`, `cabinet spec run` or the pipeline, where `CABINET_AGENT` is set) no one is there to ask, so two of the kit's global hooks refuse them:

- **`prepare-commit-msg`** (the credit hook) refuses `git commit --amend`, in every form: with `-m` or `-F` git calls the hook as it does for a new commit, so the hook also reads the git command's own arguments for `--amend` (or an abbreviation of it). `git commit -c` and `-C` are refused in a run too, since git calls the hook the same way for them. It also refuses a new commit made with `CABINET_AGENT` set (a run, or an agent outside one that commits as its role) when the message's last lines hold attribution other than Cabinet's own credit: a `Co-authored-by` line other than Cabinet's for that role, a `Claude-Session` line, or a line holding `Generated with`, in any case. It prints each such line and says to commit again without it; the body above the last lines is not read, and your own commits, with `CABINET_AGENT` unset, are never checked. The check goes with the hook: where the hook is not installed, nothing is checked. `--no-verify` does not skip this hook.
- **`pre-rebase`** refuses `git rebase` (and `git pull --rebase`).

Each runs the repo's own hook of the same name first, with the same arguments, and its failure still stops the commit or rebase. Outside a run, in your terminal or an interactive session, they change nothing. `cabinet doctor` says whether both are installed (`guardrails.run-refusal`); a hook of your own in the global hooks folder is left as it is, and then runs are not refused on that machine.

### An agent's own amend

Outside a run, an agent amends its own newest commit as `CABINET_AMEND_AS=<role> git commit --amend`. The credit hook then refuses the amend unless the newest commit's message holds exactly one Cabinet credit line, as its last line, naming that role: so an agent that skipped its check cannot rewrite another role's commit, or yours, that landed after its own. The refusal gives the reason (`HEAD is <role>'s commit`, `HEAD has no Cabinet credit line at the end`, `HEAD has more than one Cabinet credit line` or `CABINET_AMEND_AS is not a role name`) and says to commit the fix as a new commit. An allowed amend keeps the role's line, also with a new `-m` or `-F` message, unless you delete it in the editor. A new commit made with `-c` or `-C <commit>` is checked as an amend too. A commit with no credit line (credit roles off, or made where none is added) cannot be amended this way: the fix is a new commit. With `CABINET_AMEND_AS` unset, as in your own terminal, nothing is checked; in a run, every amend is refused as before.

Limits: `git rebase --no-verify` skips `pre-rebase`. In a run it is refused only by the tools whose deny rules match `--no-v`: Claude Code, Grok, Qwen Code, opencode, Cursor CLI and Gemini CLI. Codex and Antigravity are not covered (their rules match only how a command starts; both ask before any `git rebase`, which a run cannot answer), nor are the Cursor editor and a custom runner. An amend through a git alias of your own (`git config alias.fix "commit --amend"`) is not seen. Only `--amend`, or its abbreviation `--am`, `--ame` or `--amen`, given as an argument of its own counts as an amend, so a new commit whose `-m` message or path holds `--amend` or `--amount` commits. On Linux each argument is read on its own. On macOS `ps` joins the arguments with spaces, so the hook first takes out each line of a `-m` message where it stands between spaces. It takes out nothing when any word could be a `-F` or `--file` option (a message holding `-F` too), and no line from a comment line on (as the `-v` diff below the scissors line), since a line that did not come from `-m` could take out a real `--amend`. A message it cannot find there (one with a tab, say) is still read as an amend, and the refusal says to give that message with `-F <file>`. A run can turn both refusals off by setting `CABINET_AGENT` empty (`CABINET_AGENT= git commit --amend`), which no tool's deny rules catch, and an agent outside a run can leave `CABINET_AMEND_AS` unset: the hooks guard against a mistake, not an agent set on getting round them. Git has no hook for `reset` or `stash`, so those stay rules for the agents.

## What a shared workspace's files can do

In a shared workspace, or after you pull a teammate's commit, `cabinet.env`, the job files and `repos.tsv` come from someone else. They are settings, not programs: Cabinet [reads them as text](commands.md#how-cabinetenv-and-job-files-are-read) and runs nothing written in them, checks each role name, job name and local-only path before it uses one (and copies no local-only file through a symlinked folder), and `cabinet list` and `cabinet digest` run nothing of any other workspace on this machine.

Three settings are commands by design: `CABINET_RUNNER_CMD`, and a job's `COMMAND` and `AFTER`. A command you set on this machine with `cabinet new` or `cabinet config`, and the kit's own two (the brief's after-step and the scheduled runner), run as before. Any other one, or any change to one, is not approved on this machine: it does not run, by hand or on a schedule, and `cabinet job run` and the doctor say `<KEY> in <file> is not approved on this machine: run cabinet bootstrap at a terminal to see it and approve it`. Approving needs a person at a terminal: `cabinet bootstrap` shows each command's full text, every character that is not plain text as an escape, and asks; without a terminal (a schedule, an agent's shell) it approves nothing, and agents are told never to answer it. An approval is kept in `cabinet.local.env`, which git does not track, keyed with a secret only this machine holds, so it never reaches a teammate and a copied file approves nothing.

What this does not cover: a workspace's `bin/` and `.cabinet/` are code, and a shared workspace commits them with the rest. The workspace's own commands (`cabinet doctor`, `next`, `handoff`, `role`, `brief`) and the kit's own two commands run those scripts, so a pulled change to them runs on the next command or scheduled job. The doctor names a kit file that differs from the kit's (`kit.unedited`); read a pulled change to `bin/` or `.cabinet/` as code, before you run anything.

## Outside the shell

Every rule above is a shell rule, and the push gate sees only `git push`. An agent can also reach GitHub, npm or another service in ways that run no shell command, and the kit's own runs approve every tool call no rule denies, with no one there to stop one. These are the ways around the shell, what the kit covers for each, and what only your server-side settings can stop.

The paths:

- **P1 Connector and MCP tools.** A GitHub connector or MCP server can write files, push commits, open and merge pull requests and edit releases through the API with its own token; other servers deploy, send mail or take payments. No `git push` runs, so no hook runs.
- **P2 The kit's own unattended runs.** A scheduled job, `cabinet handoff run` or `cabinet spec run` approves what no rule denies, so a P1 call in a run meets no one.
- **P3 A host app or launcher with its own flags.** An app that starts the tool can pass flags that skip prompts or leave out the settings that hold the kit's rules.
- **P4 A host app or launcher with another settings folder.** `CLAUDE_CONFIG_DIR`, `CODEX_HOME`, `OPENCODE_CONFIG`, `XDG_CONFIG_HOME` or another `HOME` make the tool read a folder bootstrap never wrote.
- **P5 The agent edits its own guardrails with a file tool.** A file edit (not a shell command) on a tool's settings, the global hooks folder, `~/.gitconfig` or a repo's `.git/config`. The doctor finds most of it afterwards.
- **P6 Code the agent writes, then runs.** A script that calls the GitHub or npm API with a token it can reach. A rule sees the command line, not what the script does.
- **P7 A cloned project's tool settings.** A repo's `.mcp.json`, `.claude/settings.json`, `.codex/config.toml`, `.gemini/settings.json`, `.cursor/mcp.json`, Antigravity's `.agents/` and the like add MCP servers, hooks or looser settings for that folder.
- **P8 A publish arranged by a commit.** A commit adds a workflow under `.github/workflows/` that publishes or deploys on push or tag; your own push then publishes.
- **P9 Tools with no kit rules.** The Cursor editor, aider, goose, amp, crush and a custom runner have the push gate only.

What the kit does today:

- **The kit's runs start with no MCP servers** unless you list them in `CABINET_RUN_MCP_SERVERS` in `cabinet.env` (server names joined by commas, each of letters, digits, `_`, `.` and `-`, not starting with `-` or `.`) and approve that exact text at a terminal with `cabinet bootstrap`, as a runner command is approved. A list that is not approved, or changed since, starts no agent (`CABINET_RUN_MCP_SERVERS in cabinet.env is not approved on this machine`); a name with any other character starts no agent and is never offered for approval. Only Claude Code and Qwen Code have a switch the kit uses; the others start with every server their config holds.
- **A run never starts under another settings folder:** while `CLAUDE_CONFIG_DIR` or `CODEX_HOME` points anywhere but where bootstrap writes that tool's rules (`~/.claude`, `~/.codex`), a run starts no agent and names the variable. Not enforced, docs only: `OPENCODE_CONFIG` and `XDG_CONFIG_HOME`. A probe of opencode 2.3.2 did not show where it reads its config, so a run is not refused for either; keep both unset for scheduled runs.
- **The doctor lists MCP servers** each tool has in its own config files, and whether the kit's runs load each one (`guardrails.mcp`); account connectors are in no file it can read. It also names a cloned project's tool settings (`guardrails.clone-settings`). Both are notes.
- **MCP write tools, file edits and stored logins, by name, in Claude Code.** Bootstrap adds to `~/.claude/settings.json`:
  - a deny for each tool of the GitHub MCP server (its own list, github-mcp-server v2.2.0) whose name holds `merge`, `push`, `create_or_update`, `delete`, `release`, `publish`, `deploy` or `send`, under the server name `github`: `mcp__github__merge_pull_request`, `push_files`, `create_or_update_file`, `delete_file`, and the reads `list_releases`, `get_latest_release` and `get_release_by_tag`, refused too since their names hold `release`. A server you named otherwise is not covered by name, and GitHub's other write tools (`create_pull_request`, `create_branch`, `issue_write` and the like) hold none of the words, so only your token's scopes stop them;
  - `Edit` and `Write` denies on each settings file bootstrap writes rules to, `~/.gemini/config/hooks.json`, the global hooks folder `~/.config/git/hooks/`, `~/.gitconfig`, `~/.config/git/config`, and the `.git/config` of the workspace and each repo it lists on this machine (a repo added later gets its deny at the next `cabinet bootstrap`);
  - `Read` denies on `~/.git-credentials`, `~/.config/gh/hosts.yml` and `~/.npmrc`.

  These stop Claude Code's own file and MCP tools, as owner probes of Claude Code 2.1.330 showed, an allow of the same tool included; a shell command on the same file is a shell rule's job ([what each tool's rules block](#what-each-tools-rules-block)). Grok reads the same file, but whether it applies these is not confirmed: docs only for Grok.
- **Workflow files are hard to undo:** `cabinet repo add` lists the repo's `.github/workflows/` under "Hard to undo" in `AGENTS.md`, so a small task never touches them and a review cannot pass one without a way back. A repo's release config has no one file name across release tools: add yours with `cabinet config --hard-to-undo`.

Per tool:

- **Claude Code**: the MCP, file and read denies above. Runs get `--strict-mcp-config` and an `--mcp-config` file holding only the approved servers' entries from `~/.claude.json` (none by default), readable by you only and removed when the run ends or is stopped; an approved name it does not define starts no agent. The doctor reads `~/.claude.json`.
- **Codex**: no switch the kit uses: runs start with every server in `~/.codex/config.toml`, which the doctor reads. `CODEX_HOME` elsewhere refuses a run. MCP write denies are docs only: Codex's rules file has no MCP form, and bootstrap does not write your server entries; to turn off a server's write tools, list them in that server's `disabled_tools` in `config.toml` yourself.
- **Gemini CLI**: the kit never starts it, so its servers never load in a run. The doctor reads `~/.gemini/settings.json`.
- **Qwen Code**: runs get `--allowed-mcp-server-names` with the approved list (empty when none). The doctor reads `~/.qwen/settings.json`. MCP and file denies: docs only, not probed yet, so not added.
- **Grok**: no switch the kit uses: runs start with every server its config holds. Where Grok keeps its server list is not confirmed, so the doctor does not read it yet. It reads Claude Code's MCP and file denies from `~/.claude/settings.json`; whether it applies them is docs only, not probed yet.
- **opencode**: no switch the kit uses: runs start with every server in its config. Not enforced, docs only: where opencode 2.x keeps its server list is not confirmed (a probe found it did not list a server in `~/.config/opencode/opencode.json`), so the doctor does not read it, and on opencode 2.x it still cannot read the resolved settings. MCP and file denies: docs only, not probed yet.
- **Antigravity**: no switch the kit uses: runs start with every server its config holds, which is `~/.gemini/config/mcp_config.json` (owner probe, Antigravity 1.5.14). Docs only for now, each awaiting a confirming probe: `mcp(...)`, `write_file(...)` and `read_file(...)` denies (they held in a run; not yet tried in a session); the verb hook in `~/.gemini/config/hooks.json` (Antigravity sends every MCP call to a hook as the tool `call_mcp_tool`, which the kit's hook script now reads); and a session settings file for the kit's runs, since with `--settings` a deny in your own settings file did not hold. A `command(regex:...)` deny let its command run in a run, so the kit adds none, and the docs name no system-wide settings file. The kit's runs use no OS sandbox, `agy --sandbox` included.
- **Cursor**: no switch the kit uses. Runs never pass `--approve-mcps`, but that does not keep servers out: a probe of Cursor CLI 2026.10.22 showed `cursor-agent -p --force` loading the servers you installed and approved without it. The doctor counts Cursor as starting with every server in `~/.cursor/mcp.json`, which it reads. MCP and file denies: docs only, not probed yet.

What no tool rule covers: code the agent writes and then runs (P6); how another app starts a tool, including a host app that sets its own `HOME` or settings folder (P3, P4); MCP servers and tools by name beyond the GitHub server above, since a server can be called anything; account connectors, which live in your login, not a file, and write with their own token; and a publish set up by a workflow file, which only review sees (P8).

Planned next, not in this release, each once a probe confirms it: a hook in Claude Code and Antigravity that refuses any MCP tool whose name, server part included, holds one of the words above (a read such as `list_releases` too); the MCP write denies and file-tool denies for the other tools; and an admin settings file for Claude Code (`managed-settings.json`) and Codex (`requirements.toml`) that bootstrap writes for you to install with `sudo`. Docs only until then.

The hard boundary is on the server side, under your accounts, and the kit cannot set it: GitHub branch protection or rulesets on the default branch (no direct writes, a review you give), connector and token scopes limited to read where a tool does not need to write, and npm two-factor for publish, or trusted publishing from CI only. With those, a write that gets past every rule here still cannot land.

## Known limits

These are on the [roadmap](../ROADMAP.md):

- an archive made before 0.8.5 is encrypted with AES-256-CBC and no separate integrity check, so a change to one shows only as an unreadable archive: it still restores, saying it is not authenticated, and `backup verify` asks you to back up again ([backups](backups.md#what-a-backup-holds));
- any process of your user can read the backup passphrase from the keychain or secret store without a prompt (the deny rules stop agents in the tools above);
- the backup passphrase file, used where cron runs the schedules, is denied only to shell commands that name its folder, in Claude Code, Grok, Qwen Code, opencode and Gemini CLI: a tool's own file reader, a command that reaches it another way, and the other tools can still read it;
- opencode agent-level and project-level configs, Qwen workspace settings, and the project files of Claude Code (`.mcp.json`, `.claude/settings.json`, `.claude/settings.local.json`), Codex (`.codex/config.toml`), Gemini CLI (`.gemini/settings.json`), Cursor (`.cursor/mcp.json`, `.cursor/cli.json`) and Antigravity (the `.agents/`, `.agent/` and `.antigravity/` folders), can loosen the global rules, and the doctor checks only the global result: it names each such file in the workspace and the repos it lists on this machine (`guardrails.clone-settings`), as a note;
- on opencode 2.x the doctor cannot read the resolved rules.

## Undoing the guardrails

The guardrails are shared by every workspace on the machine, so removing a workspace leaves them. To remove them:

- **Rules in a tool's settings:** restore the `.bak.<timestamp>` copy bootstrap made next to the file, or delete the rules you no longer want (the kit's list is in each workspace's `.cabinet/guardrails/`).
- **The push gate, its helper, the hook stubs, the credit hook and `pre-rebase`:** `git config --global --unset core.hooksPath`, then delete `~/.config/git/hooks/`.
- **Codex:** remove `approval_policy` from `~/.codex/config.toml` (or delete the file when it holds only that line, as bootstrap creates it when there is none) and the kit's rules from `~/.codex/rules/default.rules` (rules bootstrap added later follow the line `# Added by cabinet bootstrap: rules from a newer Cabinet kit`).
- **Gemini:** delete `~/.gemini/policies/owner-control.toml` and remove `context.fileName` from `~/.gemini/settings.json`.
